## 职责原则与放置理由

内核拥有实际依赖关系与实例生命周期。监管器已经持有每个远端加载代的声明依赖、核心 Context 和当前 Binding；Binding 标明实际提供方加载代及实例名。因此，监管器通过现有解析结果构造反向依赖图，计算显式目标及其受影响传递闭包，保持内核查询接口原样。状态交接和确认期回滚属于监管器已有事务职责。

状态内容及写入持久性由所有者插件掌握。核心交接模式名、版本与不透明状态块；需要跨回滚保存的业务写入由插件在应答前写入持久存储，并采用新旧版本兼容的数据格式。

服务路由由核心转交，提供方加载代结束是核心掌握的事实。监管器把该事实附到路由寿命，在提供方开始清理时结束其在途调用和返回资源的调用租约。UP/1 沿用既有取消消息，宿主、SDK 和 ABI 沿用既有协议。

## R-1：状态交接范围

一次事务的保存集合覆盖本次可能重新执行 apply 的已有实例。分组替换、原生组内替换、批量替换、配置更新和连接故障恢复共用受影响集合与状态准备步骤。

对仍存活的加载代，在切换前调用导出器并保持冻结，全部快照准备成功后再触发内核重建。任一导出失败时解除本事务已取得的冻结，交回原错误。源进程已崩溃的实例采用最近成功导出的检查点；已有检查点优先于初始继承值。准备结果按实例名写入继承槽，实际 apply 消费该槽。

受影响集合来自当前绑定，命名域、Scoped 和实际最低次版本沿既有 Context 解析。候选新提供的接口按键与隔离域纳入当前缺席的可选依赖方，再沿实际绑定扩展传递闭包。候选最终保持某个实例的原纪元时，对该实例解除冻结。批量部署保留显式新增、移除与重挂载的配置语义；隐式依赖方纳入同一冻结和回滚集合。

进程故障在撤回提供方定义之前保存仍存活的依赖方，并保留本次受影响实例名。退避期间可选依赖方可以运行；恢复提供方之前再对这组实例导出，使等待期间的写入进入继承值。重启候选再次失败时也沿同一步骤保存存活依赖方，再撤回失败候选。

原生确认期内宿主退出时，回滚按原进程启动计划重新装载原库。事务的原快照覆盖确认期写入，因整个宿主退出额外受到影响的实例采用各自最近成功导出。分组替换、组内换库和批量替换共用原连接恢复步骤，旧连接上的回收通知按连接身份退出。

全栈替换的状态由两层按实例所有权持有：运行时从自身部署目录选取后端实例快照，网页部署保存各页面的冻结快照。监管器保存的受影响闭包可以包含随父实例退役的页面实例；运行时按部署目录整理持久化和后端恢复输入，页面实例的重新挂载及草稿恢复继续由网页事务执行。

## R-2：确认期状态丢弃报告

候选失败仍恢复事务开始时的原状态块。候选期间的内存状态由回滚销毁，其数据可靠性由插件的持久存储契约决定。

GroupReplaceReport、SwapReport 及批量结果增加可缺省的确认期丢弃信息：实例名列表、配置的确认期毫秒数及实际确认时长。该信息描述候选纪元在回滚中被撤销的实例，覆盖依赖方；核心依据纪元转换产生该列表。status.json 与日志记录这些名称和时长，状态内容继续留在不透明状态块中。

字段为 `discarded_confirmation: Option<ConfirmationDiscard>`，结构中包含 `instances`、`configured_ms`、`elapsed_ms`。稳定完成时记录实际进入新纪元的实例名，包括批次新增实例；从这一时刻开始计时，确认失败时生成报告。确认之前失败的事务省略该字段。运行时持久批次记录和 `status.json` 从同一次事务的类型化结果取得报告，日志只输出实例名和时长。

按 DOC-11 §3.2 的追加缺省字段规则，运行时接口升为 `cordis.runtime@1.5`，兼容 1.3、1.4 读取方。核心程序和 `cordis-types` 修订为 0.1.2；SDK 保持 0.2.1，ABI 保持 1.1，UP/1 与既有方法签名保持。管理接口的受理票据结构沿用现有契约。

## R-3：在途调用与资源

复现中的长调用由插件等待 60 秒，替换提供方后仍等待到核心约 5003 ms 截止，交回 code 6。原路由强引用保持了加载代对象，却缺少清理通知。

实现通过加载代的退役通知使经过核心转交的在途调用立即返回 code 4，旧资源的后续调用同样返回 code 4；显式调用方取消沿既有 code 7。等待期间由纪元终止通知与真实 RPC 竞争，终止路径丢弃 RPC Future，使 UP/1 发送既有取消通知。提供方的清理次序保持内核依赖语义，依赖方清理阶段仍可使用其已提交的上游服务。针对性实测中，长调用和字节流分别于约 8 ms、8–10 ms 返回 code 4。

资源调用租约绑定发出该能力的服务加载代；转交参数与转交结果分别采用调用方与提供方纪元，服务数据由插件解释。路由目录按退役标识维护出口编号集合，退役只访问该加载代的出口，并在目录锁外释放资源。编号仍保留在已分配范围内，迟到 release 保持幂等。

`cordis-routing` 复用已有 Tokio 的 watch 通知与 Future 竞争机制，依赖白名单同步列入该 crate。生命周期决定仍归监管器和内核。上述行为覆盖经核心转交的调用及服务参数、返回资源；同宿主原生直接调用沿 SDK 的效应、任务和库租约约定执行。

AU-21 的持续 GET 请求曾在加载代退役后收到 503。HTTP 插件据其掌握的方法和路由撤回事实处理这次中断：空正文 GET/HEAD 收到 code 4 时，在原请求截止时间及 `replace_grace_ms` 内等待正常撤回后的新登记，向新处理方再提交一次。进程故障撤回立即保留 503；其他方法、上传流和已开始发送的响应沿原错误路径结束。该 HTTP 语义归 `plugins/http`，修订版本为 0.1.1。

## 验收与规模

针对性测试先验证跨分组有状态下游从 100 写到 137 后，在上游替换中保持 137，再覆盖原生组内替换、批量替换、配置更新和崩溃恢复。确认期用成功应答的写入后终止候选，检查原快照恢复及丢弃报告。在途调用和流使用真实服务及资源对象，验证错误码和相对于截止时间的返回时机。

统一验收执行 fmt、clippy -D warnings、一次 workspace 全量测试并从同一输出统计、177 矩阵、unsafe 审计和 cordis-abi Miri。结果保存在 `docs/measurements/dependent-state-transitions.json`。

状态准备、反向依赖闭包、候选确认记录和原进程恢复分别为各事务共用；路由的退役索引与调用等待留在既有 routing crate。按 cloc 排除注释和空行后，内核为 4230 / 5112，supervisor 为 5867 / 6340，routing 为 821 / 926，runtime 为 5452 / 5985（代码行 / 总行）。新增职责对应现有生命周期与调用转交，继续保留在各事实掌握者。按项目规模规则，supervisor 上限调整为 6000、routing 调整为 900，随本 ADR 交设计方复核；内核上限继续为 6000。
