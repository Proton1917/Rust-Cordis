# ADR-0002 并发模型：`Send + Sync` 句柄、单一内核锁、串行调和

| 项 | 内容 |
|---|---|
| 状态 | 已接受（2026-11-11，项目所有者确认 `Send + Sync`；锁与调和的结构由本 ADR 给出） |
| 影响 | `DOC-00` `G4`、`P7`；`DOC-02` 规则 `A-1`–`A-6`、§5.1 |

## 问题

`UPSTREAM` 运行在单线程事件循环上，它的正确性依赖两点：同步代码段不被打断；回调可以任意重入内核。Rust 内核需要决定句柄能否跨线程，以及在重入存在的情况下如何保护状态。

## 选项

| 选项 | 内容 | 代价 |
|---|---|---|
| A | 单线程：`Rc`/`RefCell` 或单线程 arena，句柄 `!Send` | 只能运行在单线程执行器上；不能把上下文带入 `tokio::spawn` 的任务；`RefCell` 在重入时运行期 panic |
| B | `Send + Sync` 句柄，每个对象各自加锁 | 纤程、绑定、监听器表之间的操作跨多把锁，加锁顺序难以保证，存在死锁 |
| C | `Send + Sync` 句柄，全部状态在一把内核锁下，锁不跨越用户代码，状态迁移由单一调和循环串行执行 | 用户回调要求 `Send + Sync`；持锁区间内的操作互斥 |

## 判据

1. 内核是今后各项目的核心，这些项目会使用多线程异步运行时。
2. 重入不能造成死锁或运行期 panic（`DOC-00` `R1`）。
3. 状态迁移的顺序需要可推理：`PAPER` 算法 5 假设 `refresh` 的各步之间没有其他迁移插入。

## 决定

选 C。

- 一把锁保护 `State`。内核操作的持锁区间只读写内存中的数据结构，耗时与纤程数、监听器数成线性关系，不含 I/O。
- 调用用户代码之前解锁（规则 `A-3`）。重入的调用重新加锁，不会与自己死锁。
- 改变目标纪元的操作只入队；由一个调和者处理队列（规则 `A-5`）。这保证任一时刻只有一个执行流在做迁移判定，判据 3 成立。

## 后果

- 同一线程上的重入调用发现已有调和者时只入队，由外层调和者处理。迁移判定的顺序因此是先进先出；`UPSTREAM` 中对应的是嵌套的同步调用。两种顺序在某条用例上给出不同的可观察结果时，以用例为准调整入队位置，并在 `docs/PROGRESS.md` 记录该用例。
- 多线程执行器下任务可能在另一线程立即开始。时序相关的断言只在确定性执行器上成立（`DOC-00` `R3`）。
- 监听器的 `removed` 标志、效应的待命标志是原子变量，位于锁外。它们只承担“是否仍然有效”的判定，不承担结构修改。
