# ADR-0031 防抖窗口的批次替换与配置调和

| 项 | 内容 |
|---|---|
| 状态 | 已决定（2026-11-12） |
| 影响 | DOC-15 §3.2–§3.3；DOC-11 SW-1–SW-9；cordis.manage@1.1；M12 watch 与核心监管 |

## 要求与来源

项目的 UPSTREAM-EXT 要求将一个防抖窗口内的文件变化作为一次事务处理，失败时恢复窗口开始前的运行配置、插件版本和原状态。核心依据 Q0 负责候选准备、生命周期切换、回滚与持久化；watch 收集变化并提交管理请求。

参考提交 261c5fd 的 `cordis/packages/hmr/src` 中，`_watch` 合并窗口中的文件并串行提交事务，保留失败来源供后续变化重试。`_partition` 根据新旧模块图中共享的模块划分 ReconcileUnit，导入失败时恢复对应单位的模块缓存与解析结果；Stage 3 的 apply 失败沿内核状态保留为 Failed。Rust 版本依据本项目的整体批次要求及 DOC-11 的原快照回滚契约，在 apply 或确认期失败时恢复整批实例。Node 模块缓存、内部加载器补丁和 JS 模块图由原生库描述符、UP/1 与唯一内核的依赖记录承担对应职责。

## 管理接口

`cordis.manage` 次版本提升为 1.1，在现有方法之后追加：

```rust
async fn replace_batch(
    &self,
    replacements: Vec<(String, String)>,
    reload: bool,
    request_id: String,
) -> Result<BatchTicket>;
```

每个二元组依次为实例名和已经安装的插件引用，UP/1 参数为 `[ [[name, reference], ...], reload, request_id ]`。同一分组、同一逻辑插件的重复目标合并；引用相冲突时在生命周期变化前返回参数错误。request_id 标识一次窗口请求，重复投递同一标识沿用既有结果。

调用方需具有 `replace_batch` 授权。`reload = true` 同时检查 `reload` 授权，并把当前 `cordis.toml` 的配置变化纳入同一事务。授权始终来自人工维护的基础配置。原有 `replace` 继续提供单目标替换；接口既有方法的顺序和签名保持稳定。

## 事务步骤

1. 解析整批目标及可选的新配置，形成最终实例、分组与候选描述集合。准备全部库和进程候选，按最终集合检查配置、接口依赖和验证印记。
2. 保存原运行配置、部署引用及所有受影响实例的原状态块。导出缺席以明确的空状态记录，导出失败时对已冻结实例解冻并结束本批。
3. 原生组按本批逻辑插件合成候选定义，保留同组其余定义的身份；进程插件准备新的进程连接。全部定义提交后统一等待受影响实例稳定并执行确认期。
4. 任一候选失败时，恢复整批原定义、运行配置和原状态。恢复失败的实例保留实际失败状态，错误同时报告原操作及恢复结果。
5. 全部候选确认成功后，监管器记录内核版本已提交的事实并执行旧代码退役；管理层随后一次发布叠加层及上一版本记录，窗口至此完成。退役或持久化失败时，管理层重新准备原来源并按窗口原快照恢复。错误的内层 committed 记录监管器已确认版本，外层 committed 反映整个管理窗口的实际恢复结果。旧映像阈值重启继续采用 DOC-15 §8.7 的有状态重启条件。

原生批次保留单库替换的依赖语义：同组中未受本批变化影响的实例继续使用原定义与纪元。整个宿主的重启由既定阈值或故障恢复条件触发。

## 已确认来源与重启

构建产物的原路径可以在运行中被覆盖。运行时为实例保存独立的来源关联，内容为声明来源和已接受部署的 installed 引用；同名来源在不同实例上的已确认版本分别记录。首次装配、成功替换和窗口恢复完成后更新相应记录。

启动时，实例的声明来源保持相同时使用其最后确认的副本；人工配置显式改用其他来源时按新声明装配。批次失败后，原路径中的坏候选留供诊断和修复，原实例的已确认副本继续承担重启来源。此记录只表达代码版本关联，config、isolate、intercept、grants 等部署配置继续从当前基础配置与管理叠加层计算，配置文件保留人工维护内容。

## watch 行为

防抖结束后，watch 读取本窗口来源并完成全部安装，再按逻辑插件与分组组成一次 `replace_batch`。配置文件变化通过 `reload = true` 一并提交。来源读取或安装失败时保持当前部署，安装产生的独立副本供诊断和后续引用使用。

失败批次保存来源集合及对应的实际被拒副本；配置文件保存当时的完整内容。下次变化合并这些保留来源，逐文件、逐字节比较整批内容。全部内容相同时保持当前版本；任一来源变化时提交新的整批候选。由此，同一失败文件的重复通知保持当前状态，修复其中一个来源后可以重新提交其余相关候选。

watch 在发出请求前，将随机请求标识与窗口完整内容保存为待确认记录。标识采用 uuid 1.26.1 的 v4 生成，依赖限于 watch，最低 Rust 版本为 1.85。该标识承担请求身份，内容比较继续读取完整字节。

核心按调用方保存最近一项 `BatchOutcome { id, caller, state, error }`，返回受理凭据 `BatchTicket { id }` 前持久化 pending，响应写出后执行批次；完成后写入 succeeded 或 rejected。预约取消和核心重启把残留 pending 记录为 interrupted。Runtime 接口提升至 1.2，`RuntimeSnapshot.last_batch` 提供这些实际结果。watch 保持单个待确认窗口：pending 等待结果，succeeded 清除记录，rejected 保存拒绝副本，interrupted 允许重新提交；旧任务清理后的新实例从同一记录接续。

`watch.config.max_interrupted_retries` 限定单窗口的中断重提次数，默认 1。达到上限后保留来源并等待下一次文件变化，新的窗口使用新的请求标识。

## 验收

真实宿主场景覆盖单候选行为、同一窗口两个候选中一项失败后的整体恢复、修复后两项共同提交、配置与候选同窗失败后的配置恢复、同组无关实例纪元保持，以及同批新提供方与新使用方的接口依赖。结果记入 M12 的 PROGRESS。
