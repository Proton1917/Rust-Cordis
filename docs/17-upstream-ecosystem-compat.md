## 0 摘要

目标：开发者安装原版 cordis 插件及其正常依赖，选择兼容档案和部署配置后，由 Rust-cordis 装载和管理。插件源码、服务用法和生命周期写法不改。

按“事实由谁唯一掌握”拆分，原版生态分成三类：

1. **内核事实**：组件身份、父子树、依赖绑定、纪元、生命周期。这些已由 Rust 内核掌握，且内核移植自同一个上游提交 `261c5fd`，177 条上游用例中 174 条已移植或改写为 Rust 测试并通过，3 条不适用（`DOC-04`）。
2. **语言事实**：JS 对象、闭包、属性代理、`this`、原型、装饰器、模块缓存。这些归 Node 进程中的兼容宿主。上游 `cordis` 包中处理这些事实的代码可以直接复用，改写过的用例与 3 条“不适用”的用例（`EVT-05`、`RFL-01`、`ASC-06`）由兼容宿主按上游原文重新运行。
3. **插件**：`@cordisjs/loader`、`include`、`group`、`hmr`、`logger-console`、`timer` 等。它们只依赖 `cordis` 包的公开接口（§2.2 核对），按“核心之外一切皆插件”原样运行在兼容宿主中，不重写，只验收。

因此新增的工作集中在三者的衔接处：

- 兼容包 `cordis`：上游公开接口；语言部分复用上游源码，权威状态改由内核决定；
- 兼容宿主进程：Node 进程，内含同步桥；
- `UP/1` 的兼容能力：动态组件、同步控制请求、增量回执；
- 监管器对动态组件的登记；
- 差分验收环境。

## 2 职责裁决

### 2.1 事实与放置

依据 `AGENTS.md`“第一性原理”。每行先列决定结果的事实，再列唯一掌握者。

| 编号 | 事实 | 唯一掌握者 | 放置 |
|---|---|---|---|
| `F-1` | 组件实例身份、父子归属、实例编号 | 内核 | 不变；动态组件也在内核中登记实例 |
| `F-2` | 服务绑定、隔离域、依赖满足与否、纪元 | 内核 | 不变；兼容宿主只保存投影（§4.2） |
| `F-3` | 状态迁移（PENDING、LOADING、ACTIVE、FAILED、UNLOADING、DISPOSED）及其时机 | 内核 | 不变；宿主按回执应用 |
| `F-4` | 效应的所有者、登记顺序、释放顺序；依赖方清理完成前提供方保持可用 | 内核 | 不变；效应体与释放函数在宿主执行 |
| `F-5` | 组件定义的函数身份（同一函数是同一组件）、闭包、`this`、原型、属性代理 | 兼容宿主 | 宿主保存“函数 → 内核组件编号”表 |
| `F-6` | 事件监听器的函数值、同组派发的执行、`filter`、`thisArg` | 兼容宿主 | 宿主执行；监听器的生存期是内核中的效应 |
| `F-7` | 语言判定：`Service[check]`、`Context.filter`、配置校验 `Config['~standard']` | 兼容宿主 | 宿主判定后把结果交给内核（§4.4） |
| `F-8` | 模块解析、模块缓存、包导出、文件监视 | 兼容宿主中的 loader 与 hmr 插件 | 原样运行 |
| `F-9` | 配置文件内容、配置表达式、Include 与 Group 的组装 | loader、include、group 插件 | 原样运行；内核只收到不透明配置 |
| `F-10` | 连接、请求编号、对象编号、引用持有 | `UP/1` 两端 | 不变；新增方法见 §6 |
| `F-11` | 进程存活、重启、宿主故障后的实例回收 | 监管器 | 不变（`CP-6`） |
| `F-12` | 业务数据与规则 | 应用插件 | 不变 |

### 2.2 推论

1. **loader 等包是插件。** `loader`、`hmr`、`include`、`group` 的源码只从 `cordis` 包导入 `Context`、`Fiber`、`FiberState`、`Service`、`Component`、`Inject`、`ValidationError`、`composeError`；使用的成员为 `registry.use/get/has/resolve/replace`、`reflect.provide/notify/store`、`fiber.update/dispose/state/uid/entry`（2026-11-14 对 `261c5fd` 全文检索）。只要兼容包按原样提供这些接口，它们无需改动。`reflect.store` 是内部表，§5.1 单独处理。
2. **语言代码复用上游。** `utils.ts`、`service.ts`、`context.ts`、`reflect.ts` 的代理处理器、`fiber.ts` 中执行效应的 `_execute`、`events.ts` 的派发循环，都只处理 `F-5`–`F-7` 的语言事实，按原文复用（MIT 许可，保留版权声明）。复用避免重写带来的行为偏差。
3. **内核预计不改。** 内核已有按名称的服务、隔离、拦截与事件接口（`provide_named`、`get_named`、`isolate_named`、`intercept_named`、`on_named`），以及以闭包定义组件的 `ComponentDef::new`。动态组件由监管器构造 `ComponentDef`，其加载函数向宿主下发执行请求，不需要新的内核原语。`C1` 核实这一点；若必须改内核，先按 `AGENTS.md` 第 3 条写出只有内核掌握相关事实的证明，并经设计方确认。
4. **单一内核保持成立。** 兼容宿主的投影只用于同步读取。宿主不自行决定任何状态迁移，见 `SC-1`。

## 3 结构

### 3.1 组成

| 组件 | 位置（规划） | 职责 | 依据 |
|---|---|---|---|
| 兼容包 `cordis` | `compat/cordis-j1/` | 上游公开接口；语言部分为上游源码，权威部分调用宿主运行时 | §2.2 第 2 条 |
| 兼容宿主 | `compat/host-node/` | Node 进程插件；通信线程与执行线程；投影表；同步桥 | §4 |
| 档案与安装说明 | `compat/profiles/`、`docs/guide.md` 新增一节 | 档案文件、安装方式、包名映射 | §1.2、§7.1 |
| 监管器扩展 | `crates/cordis-supervisor` | 动态组件登记与退役、同步控制请求的处理、增量回执 | §6 |
| 差分验收环境 | `tools/compat/` | 上游参考环境与兼容环境运行同一组测试并比较 | §9 |

兼容宿主作为进程插件运行，经 `UP/1` 接入，与 `DOC-15` §4.2 的通用插口相同。宿主内的 Node 运行时只供插件使用，核心不包含它（`Q0`）。

### 3.2 三种结构保持各自的含义

| 结构 | 决定 | 掌握者 |
|---|---|---|
| 组件父子树 | 归属与清理责任 | 内核 |
| 服务依赖图 | 激活条件与依赖变化 | 内核 |
| 执行分组 | 代码所在进程、同步调用与对象共享的条件 | 部署配置；一个兼容宿主进程为一个分组 |

同一兼容宿主中的多个插件共享 JS 运行环境，在内核中仍分别拥有实例身份、依赖与效应记录。

### 3.3 部署形态

`cordis.toml` 中声明一个兼容宿主实例，其配置指向原版配置文件：

```toml
[[instances]]
name = "app"
plugin = "cordis-compat-node"
config = { profile = "J1", root = "apps/harness", config = "cordis.yml" }
```

宿主启动后创建原版根上下文，以 `@cordisjs/loader` 作为根组件读取 `cordis.yml`。此后插件的加载、Include、Group、配置更新和 HMR 都由上游插件在宿主中完成，每个组件实例同时在内核中登记。

## 4 同步语义与唯一内核的协调

### 4.1 原版中需要同步完成的操作

以 `cordis/packages/core/src` 为准：

| 操作 | 同步可观察的结果 |
|---|---|
| `ctx.set` / `ctx.provide` / `new Service(ctx, name)` | 返回后 `ctx.get(name)` 立即可见；依赖方的状态立即变为 LOADING 或 UNLOADING；`internal/service`、`internal/status` 同步派发 |
| `ctx.use(component)` | 立即返回 Fiber；`state` 已按依赖计算；组件函数在下一个微任务执行（`fiber.ts` `_reload` 中的 `await Promise.resolve()`） |
| `ctx.effect(execute)` | 效应体同步执行；返回的释放函数可立即调用，同步执行释放 |
| `ctx.on` / `ctx.emit` / `ctx.bail` | 登记后立即可派发；派发同步执行监听器并返回 |
| `ctx.get` / 属性访问 | 按 `locate` 同步解析绑定 |
| `fiber.update(config)` | 同步经 `internal/update` 链，可被监听器否决 |

上游测试依赖这些时序。例：`service.spec.ts` “pending inject” 先 `root.emit('custom-event')`，再 `await sleep()`（`setTimeout(0)`），随后断言依赖方已经执行。这要求由本宿主操作引起的全部后续状态变化都在宏任务之前完成，中间不能等待进程间消息。

### 4.2 协调规则

| 编号 | 规则 | 理由 |
|---|---|---|
| `SC-1` | 状态迁移只由内核决定。宿主执行代码并报告结果；宿主投影中的每次状态变化都来自核心的回执或请求 | `F-2`–`F-4`；保持唯一内核 |
| `SC-2` | 改变内核状态的宿主操作使用同步控制请求：执行线程阻塞等待，直到收到回执 | 保持 §4.1 的同步结果 |
| `SC-3` | 回执携带该操作在内核中引起的、与本宿主相关的全部增量，按内核提交顺序排列：绑定变化、状态迁移、待执行的加载与清理、待派发的内部事件。宿主在返回调用方之前按序应用 | 本宿主自身的写入在返回时可见 |
| `SC-4` | 回执中的加载与清理由宿主按上游时序执行：加载在微任务中执行，与上游 `_reload` 相同；清理按上游 `_unload` 的并发与逆序执行 | 由本宿主引起的连锁变化不经过宏任务，§4.1 的例子成立 |
| `SC-5` | 宿主报告加载完成、清理完成、效应释放，也使用同步控制请求，回执同样携带增量 | 状态推进与上游处在同一调用栈 |
| `SC-6` | 核心处理同步控制请求时，不等待任何宿主的响应，包括发起请求的宿主。需要其他宿主参与的后续工作（向其他宿主下发 `apply`、清理），在回执发出后经普通异步请求进行 | 被阻塞的宿主无法应答，避免死锁；与 `CP-4`、`CP-5` 一致 |
| `SC-7` | 由其他宿主或核心配置引起的变化，经普通异步消息到达，宿主在事件循环空闲时应用 | 原版没有跨进程来源，这类变化只需与本宿主的因果顺序一致 |
| `SC-8` | 宿主对读取结果使用投影缓存，键为（视图编号，服务名），由增量使之失效。缓存命中时属性访问不发请求 | 属性访问是最频繁的操作 |
| `SC-9` | 内核拒绝请求时（上下文已退役、未声明依赖等），宿主在本地构造上游对应的错误，例如 `CordisError('INACTIVE_EFFECT')`、`cannot get property "x" without inject`，并沿用上游的栈处理函数 | 错误对象与上游一致 |

`SC-6` 是死锁防护的核心条件：宿主阻塞期间，核心可能向它发来异步请求，这些请求由通信线程排队，执行线程解除阻塞后处理；核心不因此等待。

### 4.3 Node 中的同步桥

| 部件 | 职责 |
|---|---|
| 通信线程（`worker_threads`） | 独占标准输入输出；读写 `UP/1` 帧；把同步回执写入共享缓冲区并唤醒执行线程；其他消息转交执行线程的事件循环 |
| 执行线程（主线程） | 运行插件代码；发出同步控制请求后在 `Atomics.wait` 上阻塞 |
| 共享缓冲区 | `SharedArrayBuffer`，承载回执长度、回执字节与唤醒标志；超出容量时分段传递 |

关闭与故障：

- 标准输入关闭时，通信线程唤醒执行线程，执行线程退出，满足 `CP-10`；
- 同步等待设截止时间，超时后宿主按协议错误退出，由监管器按 `CP-6` 回收；
- 宿主进程崩溃时，整个分组的实例转入失败或重启，其他分组与核心不受影响（`CP-6`）。

`C1` 实测并记录以下数据：同步往返的中位数与 99 分位；启动 N 个原版插件的总时间，与上游参考环境对比。数值确定后，由项目所有者批准预算，写入档案文件。

### 4.4 语言判定的两段提交

`Service[check]` 与配置校验是 JS 函数（`F-7`），而内核在计算依赖时需要它们的结果。按 `SC-6`，核心不能在处理请求时回调宿主。因此：

1. 宿主发出 `provide` 时，内核计算受影响的依赖方。需要判定时，回执列出待判定项（依赖方视图、服务名）。
2. 宿主在本地执行判定，用下一个同步控制请求提交结果。
3. 内核按结果提交绑定与状态迁移，回执携带增量。

两段之间宿主不运行其他插件代码，原版的同步结果保持不变。依赖方位于其他宿主时，判定在提供方所在宿主执行；这种跨宿主判定是否需要支持，由 `C1` 依据实际插件决定，暂列为已知差异。

### 5.2 服务名与命名空间

上游服务名是不带版本的字符串，例如 `ctx.http`。`UP/1` 的接口名为 `<名称>@<主版本>`。

| 规则 | 内容 |
|---|---|
| 内核键 | `<档案>/<根编号>:<名称>`，例如 `J1/1:http`。档案不同或根不同的同名服务互不绑定 |
| 根编号 | 宿主中每个 `new Context()` 对应一个编号；原版应用通常只有一个根 |
| 跨语言导出 | 插件清单显式声明 `[compat.export] http = "acme.http@1"` 并提供 WIT，宿主为导出名登记一个通用调用适配对象；不声明则只在本档案内可见 |
| 跨语言导入 | 原版插件经 `[compat.import]` 把 `cordis.http@1.0` 等接口映射为本地名，宿主以远程代理承接，只开放方法调用 |
| 符号名事件 | 符号是宿主内的对象身份，只在本分组内派发；内核只记录生存期 |

### 5.3 根上下文

`new Context()` 在宿主实例下创建兼容根：内核中登记为宿主实例的子实例，`fiber.runtime` 为 `null`，未声明依赖的访问按上游根的规则放行（`reflect.ts` 中无 `runtime` 的分支）。多个根的服务按 §5.2 的根编号相互隔离。上游测试每个用例创建新根，兼容环境照此运行。

### 5.4 事件

| 派发 | 同分组监听器 | 其他分组的监听器 |
|---|---|---|
| `emit` | 宿主本地同步执行 | 按 `DOC-15` §6.3 收到通知 |
| `parallel`、`serial` | 宿主本地执行 | `J1` 中收到通知；等待远端结果列为后续 ADR |
| `bail`、`waterfall` | 宿主本地执行 | `J1` 中不参与；远端处理链需要 `next` 延续资源，列为后续 ADR |
| `internal/*` | 宿主针对本分组的 Fiber 派发，时机来自回执增量 | 跨分组状态经 `cordis.runtime@1` 读取 |

原版应用全部运行在一个分组时，事件行为与上游相同。插件需要跨分组的带返回值交互时，改用服务调用，或者放进同一分组。

### 5.5 效应

效应体在宿主同步执行（上游 `effect` 原文）。宿主把收集到的释放函数作为一条效应记录登记到内核，记录包含所有者视图、标签和父效应（`UX-5`）。释放有两条路径：

- 用户调用释放函数时，宿主同步执行本地释放，再以同步控制请求注销记录；
- 内核决定清理时，在回执或请求中列出待释放的效应及顺序，宿主执行后报告（`SC-5`）。

上游的四种效应形式（释放函数、同步迭代器、Promise、异步迭代器）均由复用的 `_execute` 处理。

## 6 协议修订

在 `hello` 的 `Describe` 中协商能力 `compat-js/1`。未协商的连接，行为与现行 `DOC-16` 完全相同，已发布的 Rust、Python、TypeScript 插件不受影响。

| 编号 | 方法或修订 | 方向 | 内容 |
|---|---|---|---|
| `UX-1` | `component_define` | H→C | 登记动态组件：宿主分配的执行引用、名称、`inject`、`provide`、是否带配置校验。返回内核组件编号 |
| `UX-2` | `component_retire` | H→C | 宿主释放最后一个引用时退役组件定义，对应内核 `Registry::forget` |
| `UX-3` | `plugin` 扩展 | H→C | 已协商的连接可用 `component: u64` 指定 `UX-1` 登记的组件。修订 `DOC-16` §13 中“组件来自已登记描述符”的限制 |
| `UX-4` | `component_replace` | H→C | 对应上游 `registry.replace`，由内核执行实例替换 |
| `UX-5` | `effect_record` | H→C | 登记已在宿主执行完毕的效应记录。现有 `effect` 方法在效应体内由核心回调宿主，与 `SC-6` 冲突，兼容连接改用本方法 |
| `UX-6` | `on` 扩展 | H→C | 登记本地监听器的生存期；监听器值留在宿主，同分组派发不经核心 |
| `UX-7` | 同步控制标记与增量回执 | H→C 请求、C→H 结果 | 请求带 `sync = true`；结果带 `delta: Vec<Delta>`，`Delta` 的种类有绑定变化、状态迁移、待加载、待清理、待判定、内部事件 |
| `UX-8` | `load_settled`、`unload_settled`、`judge` | H→C | 报告加载、清理完成（`SC-5`），提交语言判定结果（§4.4） |

逐字段定义在 `C1` 中产出，并入 `DOC-16` 新增一节。

## 7 加载、配置与热更新

### 7.1 包解析

插件代码中的 `import ... from 'cordis'` 必须解析到兼容包，且整个宿主中只有一份实例：

- 兼容包的包名为 `cordis`，导出映射与上游 4.0.0-rc.12 相同；
- 应用以 `package.json` 的别名或 `overrides` 指向兼容包；
- 安装检查遍历 `node_modules`，确认只有一份 `cordis`；发现第二份时拒绝启动，并列出路径。

CommonJS 的模块缓存以解析后的文件路径为键，别名错误会让插件拿到不同的 `Context` 类，因此包解析单独验收（`CX-6`）。安装与打包产物不得包含本机绝对路径，沿用 `ADR-0049` 的检查。

### 7.2 Loader、Include、Group

三者原样运行（§2.2 第 1 条）。配置文件、配置表达式与组装结果是 `F-9` 的事实，内核只看到各实例的不透明配置。loader 的 `fiber.entry` 等扩展字段写在宿主的 Fiber 投影对象上，不进入内核。

### 7.3 HMR 与 `watch`

| 机制 | 范围 | 执行者 |
|---|---|---|
| `@cordisjs/hmr` | 宿主内的 JS 模块：监视文件、更新模块缓存、调用 `registry.replace` | 兼容宿主中的 hmr 插件；替换由内核执行（`UX-4`） |
| `watch` 插件 | 分组整体与非 JS 插件，经 `cordis.manage@1` | 现有机制 |

兼容宿主进程本身的整体换代沿用 `watch` 与管理接口。

## 8 状态与热更新

- 代码替换、组件重新激活、业务状态迁移分别验收。
- 原版插件首先获得与上游相同的更新与清理行为。
- 需要跨进程重启保留状态的组件，经现有 `export_state` 声明状态。
- 闭包、打开的系统句柄与 JS 堆对象不迁移。宿主进程重启时这些对象重建，档案的已知差异中写明。

## 9 验收

### 9.1 差分环境

两套固定环境运行同一组测试：

| 环境 | 组成 |
|---|---|
| 参考 | 上游 `261c5fd` 的原版包，原版 Node 进程 |
| 兼容 | 兼容包与兼容宿主，经 `cordis run` 启动 |

比较的内容：

- 返回值与异常；
- 事件顺序；
- 对象身份关系；
- Fiber 状态序列；
- 清理结果。

测试代码保持上游原文。测试环境的适配（例如入口改为在兼容宿主中运行）与实现差异分开记录，后者形成缺陷与复现用例。

### 9.2 验收项

| 编号 | 场景 | 通过的判据 |
|---|---|---|
| `CX-1` | 同步纵向原型：§4.1 表中每类操作各一个最小用例，加回调重入 | 两环境逐项相同；同步往返数据已记录（§4.3） |
| `CX-2` | `packages/core/tests` 全部 16 个 spec 文件原文运行 | 全部通过；未通过项进入档案已知差异，并附理由 |
| `CX-3` | 每个兼容实例在内核中有身份：从 `cordis status` 与 `cordis.runtime@1` 读取 | 实例树与宿主中的 Fiber 树一一对应 |
| `CX-4` | 依赖由内核解析：同一服务由 Rust 插件与原版插件分别提供，原版使用方经 `[compat.import]` 获取 | 绑定、替换、卸下的行为与 `AU-29` 一致 |
| `CX-5` | 故障：插件抛错、宿主退出、同步等待超时、替换中断、迟到响应、重复释放 | 核心继续运行；其他分组继续服务；受影响实例按 `CP-6` 恢复 |
| `CX-6` | 包解析：ESM 与 CJS 混合依赖，含别名与多层依赖 | 宿主中只有一份 `cordis`；`Context` 身份一致；违规时拒绝启动 |
| `CX-7` | `loader`、`include`、`group`、`hmr` 的上游测试原文运行 | 全部通过或进入已知差异 |
| `CX-8` | 原版应用组合：装载、重配、HMR 更新、失败回滚 | 与参考环境的可观察行为相同 |
| `CX-9` | 长期运行：同一插件反复 HMR 更新 1000 次 | 内核实例数、组件定义数、宿主对象表规模回到基线 |
| `CX-10` | 回归 | 原有测试、177 条上游用例、unsafe 审计、fmt、clippy 全部通过；核心 crate 与 `cordis-abi` 若有改动，附 §2.2 第 3 条的证明 |

## 13 风险

| 编号 | 风险 | 应对 |
|---|---|---|
| `RK-1` | 同步往返过慢，原版应用启动明显变慢 | `SC-8` 缓存；`C1` 实测；必要时批量登记，由核心确认纪元后统一提交（保持 `SC-1`） |
| `RK-2` | 上游测试依赖微任务的精确次数，回执应用的时序与之不符 | `SC-4` 按上游时序安排；差异进入已知差异并附用例 |
| `RK-3` | 上游 4.0 仍是预发布版，接口可能继续变化 | 档案固定提交；新版本按新档案纳入 |
| `RK-4` | 内核与上游在个别语义上已有差异（`DOC-01` 第三部分） | 差分环境暴露后，按“兼容档案的可观察行为”裁决；需要改内核时走 §2.2 第 3 条 |
| `RK-5` | 第三方插件访问 `cordis` 未公开的内部字段 | 兼容包按需提供只读投影；无法提供的写入已知差异 |
