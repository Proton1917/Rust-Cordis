## 1 背景

第一阶段交付了一个 Rust 库 `cordis`。它实现了 `PAPER` 的可回退效应、反应式余效应和组件生命周期，177 条 `UPSTREAM` 用例全部有对应处置，`M6` 的 8 线程压力测试通过。这个库要求组件与内核编译进同一个程序。

项目所有者要求的系统形态是：

1. 核心编译成一个独立的可执行文件，长期运行，低频升级。
2. 其余功能都是单独编译的插件，以二进制文件的形式交给核心装载。插件作者不需要重新编译核心。
3. 插件可以在核心运行期间装入、卸下、替换。替换一个插件时，依赖它的插件自动重建连接，其余插件不受影响。
4. 插件的实现可以被今后的开发者或更强的 AI 整体重写。新实现满足同一份契约，就能替换旧实现。

第一阶段的内核已经提供第 3 条所需的运行时机制：`Registry::replace` 替换组件实现，余效应让依赖方随提供方的变化先清理再重建。第 1、2、4 条需要本阶段新增的三样东西：核心可执行文件、跨编译边界的二进制接口、插件契约与验证机制。

## 2 系统形态

```
cordis（核心可执行文件）
├── 内核 crates/cordis                生命周期、依赖解析、效应回退
├── 装载器 crates/cordis-loader        打开插件库、握手、租约、热替换、回滚
├── 宿主 crates/cordis-runtime         tokio 执行器、配置、目录监视、状态目录
└── ABI v1 宿主侧 crates/cordis-abi

plugins/（单独编译的插件库，.dylib / .so）
├── libkv_file.dylib       依赖 cordis-sdk，提供接口 kv@1
├── libcounter.dylib       依赖 cordis-sdk，注入接口 kv@1
└── ...
```

插件只依赖 `cordis-sdk`。`cordis-sdk` 只通过 `DOC-12` 定义的二进制接口与核心通信，不链接内核。内核的 Rust 类型从不跨越插件边界。

### 2.1 三个演化周期

系统的不同部分按不同频率变化。

| 层 | 内容 | 预期变化频率 | 兼容承诺 |
|---|---|---|---|
| 核心运行时 | 内核、装载器、宿主 | 每年一次左右 | 升级时继续接纳仍在支持期内的 ABI 主版本（`ADR-0014`） |
| 插件 ABI 与 SDK | `DOC-12`、`cordis-sdk` 的公开接口、内置接口 | 尽量不变；新增能力以次版本追加 | ABI 主版本一经冻结，布局不再改变 |
| 接口契约 | 接口 crate、契约套件、状态模式 | 随业务演进，以版本号管理 | 次版本只做追加；不兼容的变化发布新主版本 |
| 插件实现 | 插件库 | 随时 | 无。实现可以整体重写，只要通过契约套件 |

## 3 目标

| 编号 | 目标 | 验收方式 |
|---|---|---|
| `G6` | 核心以可执行文件 `cordis` 交付，按配置装载插件库 | `DOC-14` 验收场景 `AC-1` |
| `G7` | 插件与核心单独编译：插件可以使用与核心不同的 Rust 编译器版本构建 | `AC-8`：用另一个稳定版编译器构建的插件可以装载并运行 |
| `G8` | 运行中替换插件库：依赖方自动重建，未受影响的插件保持运行，替换失败自动回滚 | `AC-2`、`AC-3`、`AC-4` |
| `G9` | 替换后旧库的代码不再被调用 | `AC-2`：旧库租约在替换完成后归零 |
| `G10` | 内存中的组件状态可以跨替换、跨核心重启迁移 | `AC-2`、`AC-5` |
| `G11` | 替换前可以用契约套件验证新实现 | `AC-6`：两个独立实现通过同一套件；未通过验证的库在 `require_verified` 下被拒绝 |
| `G12` | 插件故障不拖垮核心：插件内的 panic 转换为错误 | `AC-7` |
| `G13` | 内核保持第一阶段的全部保证 | 第一阶段的全部测试与 `tools/conformance.py check --through M6` 持续通过 |

## 4 范围外

| 事项 | 说明 |
|---|---|
| 进程隔离与沙箱 | 原生插件与核心同进程，插件的段错误、死循环、内存破坏会影响整个进程（`Q8`）。WebAssembly 装载器或子进程插件作为后续可选的第二种装载器，`DOC-12` 的描述符为它保留 `format` 字段 |
| 物理卸载的保证 | 本阶段保证旧库代码不再被调用。旧库映像是否从内存移除取决于平台，不作承诺（`ADR-0012`） |
| 核心自身的热替换 | 核心升级通过有状态的重启完成：导出全部状态、退出、新核心启动、导入状态（`DOC-11` §9）。不提供连接与套接字的无缝交接 |
| 跨机器分布 | 单进程、单机 |
| Windows | 目标平台为 `aarch64-apple-darwin`（主）与 `x86_64-unknown-linux-gnu`（次） |
| 发布到 crates.io、插件市场、签名分发 | 后续工作 |

## 5 设计公理

公理按重要性排序，冲突时排前者优先（另见 §8）。

### Q1 运行时承担稳定，插件承担演化

运行时只放各插件都需要、且变化慢的机制：生命周期、依赖解析、装载、替换、状态迁移。领域功能一律写成插件。新增运行时能力前，先说明它为什么不能写成插件。这一条延续第一阶段的 `P10`。

### Q2 契约是长期资产，实现可以再生

一个插件的长期价值在它的契约：接口定义、契约套件、状态模式（`DOC-11` §2）。实现是满足契约的一份代码，可以被整体重写。契约的修改受版本规则约束（`ADR-0014`），实现的修改不受约束。

### Q3 边界上只有 ABI 类型

跨插件边界传递的值只能是 `DOC-12` 定义的类型。内核类型、标准库类型、第三方 crate 类型都不跨边界。这样插件可以使用任意编译器版本和任意依赖版本，核心也可以重写内部数据结构而不影响插件。

### Q4 指向插件库的引用持有该库的租约

任何持有插件库代码指针或数据指针的值，同时持有该库的一份租约（`ADR-0012`）。装载器以租约计数判定旧库的代码是否已经静止。

### Q5 替换先验证、后生效，失败即回滚

新库在握手、接口兼容检查、可选的契约验证都通过后才开始替换。新实例在时限内未能进入 `Active`，装载器把旧库和旧状态换回去。

### Q6 状态迁移是显式协议

插件被替换时，内核会回退它的全部效应，内存中的数据随之消失。需要保留的状态由组件通过导出器显式交出，由新实现显式接收（`ADR-0013`）。没有导出器的组件以空状态重启。

### Q7 版本并存，靠适配器过渡

ABI 主版本、接口主版本都可以同时存在多个。旧插件不需要为核心升级而重新编译；接口发生不兼容变化时，以新主版本发布，旧主版本由适配器插件继续提供。

### Q8 原生插件是可信代码

原生插件与核心同进程运行，没有沙箱。插件的可信度来自验证门（`G11`）和回滚（`Q5`），不来自隔离。需要运行不可信代码时，使用 §4 所述的后续装载器。

### Q9 `unsafe` 集中在少数 crate

内核 crate 继续不使用 `unsafe`。`unsafe` 只出现在 `cordis-abi`、`cordis-loader` 和过程宏生成的固定代码形态中，每处附 `// SAFETY:` 说明，`cordis-abi` 的测试在 Miri 下运行（`DOC-13` 规则 `B-2`）。

## 6 可替换性指标

`Q2` 的目标是让替换一个插件的代价只取决于这个插件本身。下列指标量化这一点，在 `DOC-14` 的 `M13` 中实测并记录。

| 编号 | 指标 | 定义 | 测量方法 |
|---|---|---|---|
| `RM-1` | 理解范围 | 重写一个插件需要阅读的代码行数：插件源码 + 它注入和提供的接口 crate + 契约套件 | `wc -l` 统计，按插件列出 |
| `RM-2` | 重编译范围 | 修改一个插件后需要重新编译的 crate 数 | 修改示例插件后执行 `cargo build`，统计编译的工作区 crate，预期为 1 |
| `RM-3` | 受影响实例数 | 一次替换中被重载的纤程数 | 装载器在替换完成事件中报告 |
| `RM-4` | 替换停顿 | 从开始替换到被替换实例及全部依赖方重新进入 `Active` 的时长 | 装载器计时，报告中位数与最大值 |
| `RM-5` | 验证时长 | 对新库执行契约套件的时长 | `cordis verify` 计时 |
| `RM-6` | 每次替换的常驻内存增量 | 连续替换同一插件后进程常驻内存的增长量除以替换次数 | `AC-9` 连续替换 50 次，读取进程常驻内存 |

## 7 插件粒度准则

跨插件调用比插件内部调用多出一次间接调用，参数不属于基本类型时还要经过序列化（`DOC-12` §7）。每个插件还有自己的接口、套件和状态模式需要维护。因此：

| 适合作为插件 | 适合留在插件内部 |
|---|---|
| 有稳定对外接口的子系统：存储、网络协议、渲染、编辑功能、模型调用、工具注册 | 单个函数、算法内部步骤、只服务一个插件的辅助类型 |
| 有独立的演化节奏，可能被整体替换 | 每秒调用次数很高、对延迟敏感的内部循环 |
| 规模大致在一千行到两万行之间 | 跨插件共享的可变数据结构（改为由一个插件拥有，通过接口访问） |

跨插件共享可变状态、跨插件传播内部类型、未经注入声明的隐式依赖，都会让插件之间重新耦合。`DOC-11` 的规则禁止这三种做法。

## 8 冲突裁决顺序

第二阶段的设计或实现中两条要求冲突时，按以下顺序取舍，排前者优先。

1. 内存安全：不允许出现调用已失效库代码、跨分配器释放、跨边界展开等未定义行为。
2. `PAPER` 的结构性保证与第一阶段的内核行为（`DOC-00` §6 前两项）。
3. ABI 的稳定性：冻结后的 `DOC-12` 布局不改变。
4. 替换的正确性：先验证、可回滚、旧代码静止（`Q4`、`Q5`）。
5. 插件作者的使用简洁度。
6. 性能。

## 9 风险

| 编号 | 风险 | 触发条件 | 应对 |
|---|---|---|---|
| `R7` | 调用已失效库的代码 | 旧库被关闭后，某处仍有指向它的函数指针，例如插件自行创建的线程 | 默认不关闭旧库（`ADR-0012`）；租约计数；`DOC-11` §4 的资源规则要求线程与任务绑定到效应 |
| `R8` | ABI 定义错误被冻结 | `M8` 冻结的布局存在缺陷 | 冻结前以 Miri 测试与两个方向的往返测试覆盖全部类型；冻结后的修正只能以 ABI v2 发布 |
| `R9` | 插件内的 tokio 与核心的 tokio 不是同一份 | 插件调用 `tokio::spawn` 或 tokio 的网络接口 | 插件通过 SDK 使用核心的任务派发与计时；需要 tokio 网络的插件在效应中创建并拥有自己的运行时（`DOC-11` §4） |
| `R10` | 状态迁移丢失数据 | 导出与卸载之间仍有写入 | 导出器的契约要求导出时冻结写入（`ADR-0013`）；契约套件覆盖往返迁移 |
| `R11` | 旧库映像累积占用内存 | 频繁替换，旧库不关闭 | `RM-6` 实测；运行时报告累积量；需要回收时做一次有状态重启 |
| `R12` | 验证门被绕过 | 配置关闭 `require_verified` | 默认值由部署者决定；状态报告中标明每个库是否经过验证 |
| `R13` | 插件之间重新耦合 | 跨插件共享内部类型或可变状态 | `Q3` 在类型层面阻止内部类型跨边界；§7 准则；评审 |
| `R14` | 内核为支持插件而膨胀 | 把装载、迁移逻辑写进内核 | 内核只做 `DOC-13` §2 列出的改动 `K-1`–`K-4`；第一阶段的行数上限不变 |
