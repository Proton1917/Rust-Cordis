# 核心、共享宿主与插件接入

本文规定下一版运行时的目标架构。v0.2.5 的默认分组、当前主分支和拟议接口分别见[版本页](PROGRESS.md)。业务作者使用同一套组件模型；执行位置决定调用怎样送达和故障影响范围。

## 1 组件隔离

每次挂载生成一个实例。各实例有独立上下文、已解析依赖和效应作用域。停止实例时先清理使用其服务的依赖方，再撤回该实例登记的服务、监听器与资源；重新挂载提供方会使等待中的组件恢复。应用可以单独升级一个组件。同组中依赖关系与版本都保持原样的组件继续执行。

## 2 核心进程

`Q0` 规定核心只执行自己的代码。唯一内核拥有上下文、实例树、实际依赖、生命周期和替换决定。核心按连接确认调用来源，路由不透明载荷，执行截止时间与资源回收。HTTP、用户会话、数据库内容、访问密钥和业务任务分别由终结这些操作的插件解释。

## 3 宿主与管理

一个 `cordis-host` 可以装载多个原生库。新应用以共享原生宿主作为常规部署；单独分组表达明确的进程级恢复需求。版本化配置的加载器负责区分新默认值与既有 `cordis.toml` 的按插件分组默认值。现行版本采用相同的显式 `group` 即可合组。插件宿主负责库、对象和执行线程，核心决定依赖是否满足以及哪个实例执行 `apply`。

授权管理插件经 `cordis.manage` 提交装载、替换、配置变更和回滚请求；`watch` 收集一个防抖窗口内的来源变化，向同一入口提交批次。进程组属于部署配置，逻辑上下文中的 `scope`、`isolate` 和 `intercept` 决定服务可见范围。

### 新旧部署清单的解析

新清单在顶层使用 `format_version = 2`。缺省格式号和显式旧格式均走现有读取规则。新清单中的原生实例省略 `group` 时，部署工具将其划入应用的共享原生组；配置了 `group` 的实例按该值合组。脚本程序与浏览器页面仍使用相应语言环境。迁移工具展示旧实例到新宿主的对应关系，首次启用新格式时由应用确定可共同重启的范围。该格式为设计输入，现行 v0.2.5 的写法见[使用指南](guide.md)。

例如编辑器把索引、排版与导出作为三个插件发布。索引常规更新时，消费索引的排版实例重新绑定，其他服务继续处理已有请求。若索引库的原生进程故障导致共享宿主结束，宿主中全部实例重新装载；核心按真实绑定撤回受影响服务。文档草稿和已持久提交的编译任务依各自插件的数据契约恢复。

## 4 调用路径

| 位置 | 绑定与执行 |
|---|---|
| 同一原生宿主 | 核心先解析服务。新契约由宿主本地按稳定方法身份分派；消费方和提供方可以独立编译。旧库依 ABI v1 执行。 |
| 不同宿主或脚本进程 | 核心按 UP/1 对象编号转发。参数与返回值遵循相同业务契约；Python 和 Node 使用各自解释器。 |
| 浏览器页面 | HTTP 插件终结 WebSocket。每个页面拥有独立连接与组件实例，网页的依赖与清理同样由核心协调。 |

同组共享地址空间和执行资源。框架可以隔离普通组件错误；原生进程崩溃会结束同一宿主中的全部实例。核心撤回该连接的绑定，使相关依赖方进入等待，按策略重启整个宿主。上游 TS Cordis 的组件行为是参照目标，逐插件内存沙箱属于另一种运行模型。

## 5 资源与恢复

连接持有在途请求、发送队列和临时资源引用。配额在真正的信任边界执行，一次调用携带同一个截止时间。独立实例按实例回收，连接关闭时回收仍归该连接所有的资源。软件发布选择了运行时与协议版本，部署者配置容量及重启预算。[UP/1](16-up1-protocol.md)

核心记录已确认部署和各实例最近成功导出的检查点。启动时从这些来源重建实例。业务提交的真实性由数据所有者决定：完成写入的插件按操作标识提供结果查询，网络故障后的调用方据此恢复。发布状态文件失败进入诊断通路。

## 6 原生调用与编译边界

新版原生设计把业务方法从机器函数表中移出。SDK 保留类型化调用，宿主与库之间使用固定入口、有界参数、完成通知和可回收的资源句柄。小结果随调用返回，文件或增长型集合通过流或快照引用读取。[ABI 设计](12-abi-v1.md)

## 7 接口定义

业务接口按名称、主次版本、方法名与参数结果类型定义。WIT 生成器和本地绑定共用类型模型；影响已有调用方的语义变化使用新主版本。独立插件可以用真实提供方和调用方核验接口升级。

## 8 替换与回滚

运行时用候选的最终依赖关系准备一次切换。统一计算受影响的实例，保存需要继承的状态，交由内核清理旧实例并激活新定义。纯版本替换以预期服务恢复为成功；用户主动移除依赖时，等待中的实例也是成功结果。恢复原部署时使用本次事务开始时的状态，已经提交到业务存储的结果仍由业务所有者解释。

## 9 插件产物

原生插件交付平台动态库和描述信息；脚本插件交付入口、解释器要求及依赖；网页插件交付浏览器资源。构建工具以构建系统实际返回的产物定位程序，部署配置标识实例、版本和资源目录。

## 10 SDK

SDK 封装生命周期调用、服务访问、错误与资源所有权。Rust 的异步执行细节停留在其拥有者一侧；HTTP 客户端等需要 Tokio 的插件由 SDK 提供适配。Python 与 TypeScript 各保留语言习惯，跨语言的服务与状态采用共同契约。

## 11 前端插件与全栈插件

HTTP 插件管理静态资源、页面连接与路由；浏览器管理模块和 DOM。核心掌握可信页面来源与父子实例关系。后端和页面作为同一部署单元更新时，运行时协调状态保存、切换和恢复。页面草稿由页面组件导出，已提交数据由后端插件保存。[页面实例的真实场景](design/flow/index.html)

## 12 构建、部署与兼容

构建工程与部署目录可以分开。工具接收部署清单、源码工作区位置与资源声明，解析原生库、网页 bundle 及固定运行时版本，组装一个可在新目录启动的包。现有安装通过公开离线查询提供最近确认的程序绑定。ABI v1 的支持期和独立恢复组由交付清单明确表达。[工具链](13-runtime-architecture.md) · [现行使用手册](guide.md)

### 程序与状态的独立版本

部署记录指出“程序来自哪里”，业务回执指出“哪一次写入已经生效”，组件检查点指出“新实例从何处继续”。后继实例读取状态时检查模式与版本；应用安装工具读取运行时的公开绑定；调用方按业务标识查询数据。三种读取分别有明确的所有者和错误边界。示例见[程序绑定查询](guide.md#停机后的程序绑定查询)。
