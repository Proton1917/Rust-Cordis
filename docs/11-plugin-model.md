## 1 术语

| 术语 | 定义 |
|---|---|
| 插件库 | 一个以 `crate-type = ["cdylib"]` 编译、导出 `DOC-12` §3 入口符号的动态库文件。一个插件库可以包含多个组件 |
| 插件名 | 插件库在描述符中声明的逻辑名称，例如 `kv`。同一核心内唯一；`kv-mem` 与 `kv-file` 两个实现 crate 使用同一插件名 `kv` 和组件名 `kv-store` |
| 组件 | 插件库导出的一个组件定义，对应内核的 `ComponentDef`。全名为 `<插件名>/<组件名>` |
| 实例 | 一个组件按一份配置挂载后的纤程。实例名来自 `cordis.toml` 的条目名（§10） |
| 接口 | 跨插件的服务类型，以 `<名称>@<主版本>.<次版本>` 标识，例如 `kv@1.0`。由接口 crate 定义 |
| 接口 crate | 只包含接口 trait、事件类型、数据类型定义的普通 Rust crate，用 `cordis-sdk` 的宏标注。提供方与使用方都依赖它 |
| 契约套件 | 针对一个接口主版本的验证程序，本身也是一个插件库（§8） |
| 状态模式 | 组件导出的状态的名称与版本，例如 `kv-file.snapshot` 版本 `2` |
| 宿主 | 核心可执行文件中实现 `DOC-12` 宿主虚表的一侧 |

## 2 插件的四个组成部分

| 组成部分 | 内容 | 所在位置 | 稳定性 |
|---|---|---|---|
| 接口契约 | 插件提供和注入的接口、事件；每个方法的输入输出、错误、行为语义的文字说明 | 接口 crate 的源码与文档注释 | 受 §3 版本规则约束 |
| 实现 | 组件的 Rust 源码 | 插件 crate | 可整体重写 |
| 验证规范 | 契约套件：对接口的行为断言，覆盖正常路径、错误路径、并发、状态迁移往返 | 契约套件 crate（`<接口名>-contract`） | 随接口主版本演进 |
| 生命周期契约 | 组件在加载、卸载、替换时的行为：注入哪些接口、登记哪些效应、导出什么状态、接受哪些状态版本 | 插件 crate 中 `Component` 实现的声明部分与文档注释 | 状态模式受 §5 版本规则约束 |

重写一个插件时，阅读范围是前三项加上原实现的生命周期声明。原实现的代码只作参考。

## 3 接口与版本

### 3.1 标识

接口以 `<名称>@<主版本>.<次版本>` 标识。名称由小写字母、数字、`-`、`.` 组成。`cordis.` 前缀保留给运行时内置接口（`DOC-13` §5.3）。

### 3.2 次版本：只做追加

在同一主版本内，下列修改允许，次版本号加一：

1. 在接口 trait 末尾追加方法。追加的方法在虚表末尾（`DOC-12` §7.2）。
2. 为数据类型追加带默认值的字段（数据类型以自描述格式编码，`DOC-12` §7.3）。
3. 为事件的载荷追加带默认值的字段。

除此以外的修改都属于不兼容修改，包括删除或改名方法、修改参数类型、改变已有方法的行为语义。

### 3.3 主版本：不兼容修改

不兼容修改发布新主版本，例如 `kv@2.0`。新旧主版本是两个不同的接口，可以同时存在于一个核心中。过渡方法：

- 提供方插件同时提供 `kv@1` 与 `kv@2`；或者
- 一个适配器插件注入 `kv@2`、提供 `kv@1`，让尚未升级的使用方继续工作。

### 3.4 注入时的版本匹配

使用方注入 `kv@1.2` 表示需要主版本 1、次版本不低于 2。提供方提供 `kv@1.5` 时匹配；提供 `kv@1.1` 时不匹配，使用方保持 `Pending`，运行时日志记录版本不足。使用方调用超出提供方次版本的方法时，SDK 在调用前检查虚表长度并返回错误，不调用无效的函数指针（`DOC-12` §7.2）。

装载器将最低次版本条件写入该使用方的内核依赖声明谓词，各使用方共享同一个 `<名称>@<主版本>` 服务绑定并分别判断满足性。谓词在内核锁外读取宿主保存的接口版本，实际匹配的绑定进入该使用方的 `committed` 视图（`ADR-0016`）。

`DependencyV1.required = 0` 表示可选依赖。接口缺席或次版本不足时，组件仍可激活，该项的纪元槽为 `0`，读取交回缺席错误。接口出现、消失或被替换时，组件随纪元变化重新加载。可选接口存在期间，使用方登记到真实绑定的依赖方集合，提供方等待其清理后继续卸载。`required = 1` 使用必需依赖语义。

## 4 资源规则

插件库可能被替换，旧库的代码随后不再被调用。下列规则保证插件持有的资源都随实例的停用而释放，且不会在旧库静止后继续运行旧代码。

| 编号 | 规则 | 违反后的后果 |
|---|---|---|
| `PR-1` | 插件创建的异步任务通过 `ctx.spawn` 派发。派发的任务归属于当前效应，效应回退时内核等待它结束或取消 | 用其他方式派发的任务在库替换后可能仍运行旧代码 |
| `PR-2` | 插件创建的系统线程通过 `ctx.spawn_thread` 创建，或在一个效应中创建并在该效应的 `defer` 中通知退出并 `join` | 同上 |
| `PR-3` | 插件需要 tokio 的网络、文件接口时，在一个效应中创建自己的 tokio 运行时，在 `defer` 中关闭。不调用依赖全局运行时的 `tokio::spawn` | 插件内的 tokio 与核心的 tokio 是两份代码，调用全局 `tokio::spawn` 会因找不到运行时而 panic（`R9`） |
| `PR-4` | 插件的全局可变状态（`static`）只用作缓存。需要跨替换保留的数据通过状态导出器交出（§5） | 替换后新库从全新的 `static` 开始，旧数据丢失 |
| `PR-5` | 插件之间只通过注入的接口和事件交互，不交换原始指针，不共享 `static` | 破坏 `Q3`，替换后可能访问已失效的数据 |
| `PR-6` | 文件、套接字等操作系统资源在效应中打开，在 `defer` 中关闭 | 替换后资源泄漏，或新旧实例争用同一资源 |
| `PR-7` | 插件的持久化数据写在运行时为它分配的数据目录下（内置接口 `cordis.data-dir@1`） | 不同插件的数据混放，迁移和回滚无法定位 |
| `PR-8` | 插件以 `panic = "unwind"` 编译 | 以 `abort` 编译的插件中任何 panic 都会终止整个核心。装载器默认拒绝此类插件（`DOC-12` §10） |

`PR-1`、`PR-2`、`PR-6` 与第一阶段的可回退效应是同一个要求：组件对环境的一切修改都登记为效应。

## 5 状态迁移协议

### 5.1 对象

| 对象 | 定义 |
|---|---|
| 导出器 | 组件在 `apply` 中通过 `ctx.export_state(schema, version, f)` 登记的效应。`f` 返回一份可序列化的快照 |
| 状态块 | 导出器产生的数据：模式名、版本号、自描述编码的字节（`DOC-12` §7.3） |
| 继承状态 | 新实例在 `apply` 中通过 `ctx.inherited_state()` 读到的状态块，没有时为 `None` |

导出器是效应，因此它随实例的停用而撤销，不会被调用到已经停用的实例上。

### 5.2 时机

导出发生在以下两种场合：

1. 热替换步骤 `SW-5`（§6）：对旧库每个实例调用导出器。
2. 核心有序退出（§9）：对全部实例调用导出器，状态块写入状态目录。

继承发生在以下两种场合：

1. 热替换后新实例的 `apply`。
2. 核心启动时，实例的 `apply` 读到状态目录中对应实例名的状态块。

### 5.3 导出器的契约

1. 导出器被调用时，组件冻结写入：此后到实例停用之间到达的写请求返回错误，或排队到新实例。理由：导出后的写入不会出现在状态块中（`R10`）。
2. 导出器在时限内返回（默认 5 秒，配置项 `export_timeout_ms`）。超时视为导出失败。
3. 导出失败时替换中止，旧实例解除冻结，继续运行。

SDK 为第 1 条提供辅助：`ctx.export_state` 返回一个冻结标志，组件的写路径检查它。

### 5.4 继承方的契约

1. 新实例声明它接受的模式名与版本范围。状态块的模式名不同或版本不在范围内时，新实例按自身代码决定转换或拒绝。
2. 新实例拒绝继承状态时，`apply` 返回错误，替换按 §7 回滚。
3. 版本升级的转换代码写在新实现中。旧实现不需要知道新版本。

### 5.5 回滚时的状态

回滚使用替换开始时导出的原状态块，不使用新实例产生的任何状态。装载器保留原状态块，直到新实例连续保持 `Active` 达到确认时长（配置项 `confirm_ms`，默认 10 秒）。

## 6 热替换步骤

输入：一个正在运行的插件库 `L_old` 和一个新的插件库文件 `F_new`，二者声明相同的插件名。

| 步骤 | 操作 | 输出 | 检查 |
|---|---|---|---|
| `SW-1` | 把 `F_new` 复制到 `.cordis/lib/candidate-<序号>.<扩展名>`；序号在该目录中单调递增，启动时接续已有序号；握手取得逻辑插件名后把同一副本重命名为 `<插件名>-<序号>.<扩展名>` | 唯一路径的副本 | 每个候选拥有独立的装载路径，重命名保留同一文件内容 |
| `SW-2` | 配置 `require_verified = true` 时读取验证印记（§8），在打开库之前完成字节比对；握手取得接口声明后核对套件覆盖范围 | 印记有效或拒绝 | 候选副本与已验证副本逐字节相同，套件覆盖候选提供的接口主版本 |
| `SW-3` | 打开副本，读取入口符号，按 `DOC-12` §3 握手，读取描述符 | 新库描述符 `D_new` | ABI 版本受支持；`panic` 策略为 `unwind`；插件名一致 |
| `SW-4` | 接口兼容检查：`L_old` 当前提供且有使用方的每个接口，`D_new` 都提供同一主版本且次版本不低于原值 | 通过或拒绝 | 拒绝时未改变任何运行状态 |
| `SW-5` | 对 `L_old` 的每个实例调用导出器（§5） | 原状态块集合 | 任一导出失败则中止，解除冻结 |
| `SW-6` | 由 `D_new` 构造新组件定义，对每个组件调用内核 `Registry::replace(old, new)` | 被替换的实例列表 | 内核按余效应语义先让依赖方清理，再卸载、重载 |
| `SW-7` | 等待被替换实例与依赖方稳定，时限 `swap_timeout_ms`（默认 30 秒） | 全部 `Active`，或失败 | 失败或超时转 §7 回滚 |
| `SW-8` | 确认期：新实例保持 `Active` 达到 `confirm_ms` | 替换确认 | 确认期内失败转 §7 回滚 |
| `SW-9` | 释放原状态块；`L_old` 的租约归零后记录“旧代码静止”；按 `unload` 策略处理库映像（`ADR-0012`） | 替换报告：`RM-3`、`RM-4`、租约归零耗时 | 报告写入日志与 `status.json` |

步骤 `SW-1`–`SW-4` 保持实例、纪元和服务绑定原状。`SW-5` 进入可逆的写入冻结阶段；导出失败时对已进入导出的实例执行解冻，旧实例继续运行。`SW-6` 开始提交生命周期变化。

## 7 回滚

触发条件，满足任一项：

- `SW-7` 中有被替换实例进入 `Failed`，或在时限内未进入 `Active`；
- `SW-8` 确认期内有被替换实例离开 `Active` 且原因不是依赖缺失。

操作：

1. 用 `L_old` 的组件定义再次调用 `Registry::replace(new, old)`。
2. 旧实例的 `apply` 继承 §5.5 保留的原状态块。
3. 新库按 `SW-9` 的规则静止。
4. 记录回滚原因，`status.json` 中该插件标记为“已回滚”，`.cordis/lib/` 保留被拒副本。文件监视器将后续候选与被拒副本完整逐字节比较，内容一致时保持当前状态，内容变化时处理新候选。

回滚本身失败时，该插件的实例停在 `Failed`，其余插件不受影响，日志记录两次失败的原因。

## 8 验证门

### 8.1 契约套件

契约套件是一个插件库。它注入被测接口（例如 `kv@1`），在 `apply` 中执行断言，通过内置接口 `cordis.contract@1` 报告每条断言的结果。套件可以要求被测实现做一次状态导出与继承往返，以验证 §5 的协议。

状态往返采用两个阶段：套件在阶段 0 请求往返并交回 apply，宿主停用套件后导出与重启被测实例，再以阶段 1 挂载套件验证继承结果。`stage`、`request_state_roundtrip` 与最终 `finish` 的接口约定见 ADR-0017。

### 8.2 `cordis verify`

```bash
cordis verify --plugin plugins/libkv_file.dylib --suite contracts/libkv_contract.dylib [--config <被测实例的配置>]
```

1. 在一个子进程中启动一个空的核心实例，数据目录为临时目录（位于状态目录下）。
2. 装载被测库和套件库，挂载二者，等待套件报告完成。
3. 输出每条断言的结果与 `RM-5`。
4. 全部断言通过时，把被测库复制到 `.cordis/verified/<插件名>-<序号>.<扩展名>`，写印记文件 `<被测库文件名>.verified.json`：已验证副本路径、套件插件名与版本、覆盖的接口主版本、断言数和时间。多个套件的结果记录为同一副本下的套件列表。

使用子进程的理由：被测库是尚未验证的原生代码，可能使进程崩溃。

### 8.3 印记的使用

`require_verified = true` 时，`SW-2` 对候选库与印记中的已验证副本执行完整字节比对，并检查套件列表覆盖该库提供的每个接口主版本。运行时在 `.cordis/verified/` 保留作为验证依据的副本。

## 9 核心升级与有序退出

核心收到 `SIGTERM` 或 `SIGINT` 时：

1. 停止文件监视，不再开始新的替换；等待进行中的替换结束或回滚。
2. 对全部实例调用导出器，状态块写入 `state/<实例名>.state`。
3. 释放根纤程，等待全部实例 `Disposed`。
4. 退出。

核心启动时，每个实例的 `apply` 继承 `state/<实例名>.state`，读取后该文件移入 `state/consumed/`。

升级核心的步骤：停止旧核心（上述 1–4），替换核心可执行文件，启动新核心。新核心支持的 ABI 主版本范围覆盖现有插件时，插件不需要重新编译（`ADR-0014`）。

## 10 声明式配置

核心读取 `cordis.toml`。

```toml
[runtime]
plugin_dir = "plugins"          # 插件库所在目录，被监视
state_dir = "state"             # 状态块与插件数据目录
require_verified = false
swap_timeout_ms = 30000
confirm_ms = 10000
export_timeout_ms = 5000
unload = "never"                # never | when-unleased，见 ADR-0012

[instance.store]                 # 实例名 store
plugin = "kv"                    # kv-mem 与 kv-file 的共同插件名
component = "kv-store"           # 组件名
config = { path = "kv" }         # 交给组件的配置，以自描述格式编码后传入

[instance.counter]
plugin = "counter"
component = "counter"
config = { interval_ms = 100 }
```

配置文件或插件目录变化时，运行时计算目标状态与当前状态的差异，并按下表执行。

| 变化 | 运行时的操作 |
|---|---|
| 新增实例条目 | 挂载 |
| 删除实例条目 | 释放该实例 |
| 实例的 `config` 变化 | `Fiber::update` |
| 实例的 `plugin` 或 `component` 变化 | 释放旧实例，挂载新实例，状态不迁移 |
| 插件目录中出现插件名已装载的新文件 | 热替换（§6） |
| 插件目录中出现新插件名的文件 | 装载库，挂载引用它的实例 |
| 插件目录中的文件被删除 | 不操作。已装载的库继续运行，直到配置不再引用它 |

这一层就是 `PAPER` §4.2 的组件加载器，它本身由运行时以普通组件的形式挂载在内核上。
