## 1 术语

| 术语 | 定义 |
|---|---|
| 插件库 | 一个以 `crate-type = ["cdylib"]` 编译、导出 `DOC-12` §3 入口符号的动态库文件。一个插件库可以包含多个组件 |
| 插件名 | 插件库在描述符中声明的逻辑名称，例如 `kv`。同一核心内唯一；`kv-mem` 与 `kv-file` 两个实现 crate 使用同一插件名 `kv` 和组件名 `kv-store` |
| 组件 | 插件库导出的一个组件定义，对应内核的 `ComponentDef`。全名为 `<插件名>/<组件名>` |
| 实例 | 一个组件按一份配置挂载后的纤程。实例名来自 `cordis.toml` 的条目名（§10） |
| 接口 | 跨插件的服务类型，以 `<名称>@<主版本>.<次版本>` 标识，例如 `kv@1.0`。由接口 crate 定义 |
| 接口 crate | 只包含接口 trait、事件类型、数据类型定义的普通 Rust crate，用 `cordis-sdk` 的宏标注。提供方与使用方都依赖它 |
| 契约套件 | 针对一个接口主版本的验证程序，本身也是一个插件库（§8） |
| 状态模式 | 组件导出的状态的名称与版本，例如 `kv-file.snapshot` 版本 `2` |
| 宿主 | cordis-host，执行核心指令并实现 DOC-12 的原生宿主虚表；生命周期由核心中的唯一内核决定 |

## 2 插件的四个组成部分

| 组成部分 | 内容 | 所在位置 | 稳定性 |
|---|---|---|---|
| 接口契约 | 插件提供和注入的接口、事件；每个方法的输入输出、错误、行为语义的文字说明 | 接口 crate 的源码与文档注释 | 受 §3 版本规则约束 |
| 实现 | 组件的 Rust 源码 | 插件 crate | 可整体重写 |
| 验证规范 | 契约套件：对接口的行为断言，覆盖正常路径、错误路径、并发、状态迁移往返 | 契约套件 crate（`<接口名>-contract`） | 随接口主版本演进 |
| 生命周期契约 | 组件在加载、卸载、替换时的行为：注入哪些接口、登记哪些效应、导出什么状态、接受哪些状态版本 | 插件 crate 中 `Component` 实现的声明部分与文档注释 | 状态模式受 §5 版本规则约束 |

重写一个插件时，阅读范围是前三项加上原实现的生命周期声明。原实现的代码只作参考。

## 3 接口与版本

### 3.1 标识

接口以 `<名称>@<主版本>.<次版本>` 标识。名称由小写字母、数字、`-`、`.` 组成。`cordis.` 前缀保留给运行时内置接口（`DOC-13` §5.3）。

### 3.2 次版本：只做追加

在同一主版本内，下列修改允许，次版本号加一：

1. 在接口 trait 末尾追加方法。追加的方法在虚表末尾（`DOC-12` §7.2）。
2. 为数据类型追加带默认值的字段（数据类型以自描述格式编码，`DOC-12` §7.3）。
3. 为事件的载荷追加带默认值的字段。

除此以外的修改都属于不兼容修改，包括删除或改名方法、修改参数类型、改变已有方法的行为语义。

### 3.3 主版本：不兼容修改

不兼容修改发布新主版本，例如 `kv@2.0`。新旧主版本是两个不同的接口，可以同时存在于一个核心中。过渡方法：

- 提供方插件同时提供 `kv@1` 与 `kv@2`；或者
- 一个适配器插件注入 `kv@2`、提供 `kv@1`，让尚未升级的使用方继续工作。

### 3.4 注入时的版本匹配

使用方注入 `kv@1.2` 表示需要主版本 1、次版本不低于 2。提供方提供 `kv@1.5` 时匹配；提供 `kv@1.1` 时不匹配，使用方保持 `Pending`，运行时日志记录版本不足。使用方调用超出提供方次版本的方法时，SDK 在调用前检查虚表长度并返回错误，不调用无效的函数指针（`DOC-12` §7.2）。

装载器将最低次版本条件写入该使用方的内核依赖声明谓词，各使用方共享同一个 `<名称>@<主版本>` 服务绑定并分别判断满足性。谓词在内核锁外读取宿主保存的接口版本，实际匹配的绑定进入该使用方的 `committed` 视图（`ADR-0016`）。

`DependencyV1.required = 0` 表示可选依赖。接口缺席或次版本不足时，组件仍可激活，该项的纪元槽为 `0`，读取交回缺席错误。接口出现、消失或被替换时，组件随纪元变化重新加载。可选接口存在期间，使用方登记到真实绑定的依赖方集合，提供方等待其清理后继续卸载。`required = 1` 使用必需依赖语义。

## 4 资源规则

插件库可能被替换，旧库的代码随后不再被调用。下列规则保证插件持有的资源都随实例的停用而释放，且不会在旧库静止后继续运行旧代码。

| 编号 | 规则 | 违反后的后果 |
|---|---|---|
| `PR-1` | 插件创建的异步任务通过 `ctx.spawn` 派发。派发的任务归属于当前效应，效应回退时内核等待它结束或取消 | 用其他方式派发的任务在库替换后可能仍运行旧代码 |
| `PR-2` | 插件创建的系统线程通过 `ctx.spawn_thread` 创建，或在一个效应中创建并在该效应的 `defer` 中通知退出并 `join` | 同上 |
| `PR-3` | 插件需要 tokio 的网络、文件接口时，在一个效应中创建自己的 tokio 运行时，在 `defer` 中关闭。不调用依赖全局运行时的 `tokio::spawn` | 插件内的 tokio 与核心的 tokio 是两份代码，调用全局 `tokio::spawn` 会因找不到运行时而 panic（`R9`） |
| `PR-4` | 插件的全局可变状态（`static`）只用作缓存。需要跨替换保留的数据通过状态导出器交出（§5） | 替换后新库从全新的 `static` 开始，旧数据丢失 |
| `PR-5` | 插件之间只通过注入的接口和事件交互，不交换原始指针，不共享 `static` | 破坏 `Q3`，替换后可能访问已失效的数据 |
| `PR-6` | 文件、套接字等操作系统资源在效应中打开，在 `defer` 中关闭 | 替换后资源泄漏，或新旧实例争用同一资源 |
| `PR-7` | 插件的持久化数据写在运行时为它分配的数据目录下（内置接口 `cordis.data-dir@1`） | 不同插件的数据混放，迁移和回滚无法定位 |
| `PR-8` | 插件以 `panic = "unwind"` 编译 | `abort` 策略的 panic 会终止该插件所在的宿主进程，同组插件共同退出。装载器默认拒绝此类插件（`DOC-12` §10） |

`PR-1`、`PR-2`、`PR-6` 与第一阶段的可回退效应是同一个要求：组件对环境的一切修改都登记为效应。

## 5 状态迁移协议

### 5.1 对象

| 对象 | 定义 |
|---|---|
| 导出器 | 组件在 `apply` 中通过 `ctx.export_state(schema, version, f)` 登记的效应。`f` 返回一份可序列化的快照 |
| 状态块 | 导出器产生的数据：模式名、版本号、自描述编码的字节（`DOC-12` §7.3） |
| 继承状态 | 新实例在 `apply` 中通过 `ctx.inherited_state()` 读到的状态块，没有时为 `None` |

导出器是效应，因此它随实例的停用而撤销，不会被调用到已经停用的实例上。

### 5.2 时机

导出发生在以下场合：

1. 热替换步骤 `SW-5`（§6）：对旧库每个实例调用导出器。
2. 核心有序退出（§9）：对全部实例调用导出器，状态块写入状态目录。
3. 定期检查点（CP-11）：按 `checkpoint_ms` 导出状态并保存，完成后解除写入冻结。

继承发生在以下两种场合：

1. 热替换后新实例的 `apply`。
2. 核心启动时，实例的 `apply` 读到状态目录中对应实例名的状态块。

### 5.3 导出器的契约

1. 导出器被调用时，组件冻结写入：此后到实例停用之间到达的写请求返回错误，或排队到新实例。理由：导出后的写入不会出现在状态块中（`R10`）。
2. 导出器在时限内返回（默认 5 秒，配置项 `export_timeout_ms`）。超时视为导出失败。
3. 导出失败时替换中止，旧实例解除冻结，继续运行。

SDK 为第 1 条提供辅助：`ctx.export_state` 返回一个冻结标志，组件的写路径检查它。

### 5.4 继承方的契约

1. 新实例声明它接受的模式名与版本范围。状态块的模式名不同或版本不在范围内时，新实例按自身代码决定转换或拒绝。
2. 新实例拒绝继承状态时，`apply` 返回错误，替换按 §7 回滚。
3. 版本升级的转换代码写在新实现中。旧实现不需要知道新版本。

### 5.5 回滚时的状态

回滚使用替换开始时导出的原状态块，不使用新实例产生的任何状态。装载器保留原状态块，直到新实例连续保持 `Active` 达到确认时长（配置项 `confirm_ms`，默认 10 秒）。

## 6 热替换步骤

输入：一个正在运行的插件库 `L_old` 和一个新的插件库文件 `F_new`，二者声明相同的插件名。

核心监管器安排验证、状态导出、依赖清理、切换与回滚；原生宿主按指令准备或退役库、执行 apply 和回调。组内服务依赖同样由核心内核解析，直接方法调用保持本地 ABI 路径。完整进程替换在新进程握手与实例稳定后终止旧进程；原生库的组内替换沿下表执行。

核心在启动时按配置建立实例。运行中的安装、替换、回滚和配置重读由持有授权的插件调用 `cordis.manage@1`；开发时的文件变化由 `watch` 插件观察并提交这些请求。管理操作经过同一串行事务队列，按当前实例与依赖决定受影响范围。

| 步骤 | 操作 | 输出 | 检查 |
|---|---|---|---|
| `SW-1` | 把 `F_new` 复制到 `.cordis/lib/candidate-<序号>.<扩展名>`；序号在该目录中单调递增，启动时接续已有序号；握手取得逻辑插件名后把同一副本重命名为 `<插件名>-<序号>.<扩展名>` | 唯一路径的副本 | 每个候选拥有独立的装载路径，重命名保留同一文件内容 |
| `SW-2` | 配置 `require_verified = true` 时读取验证印记（§8），在打开库之前完成字节比对；握手取得接口声明后核对套件覆盖范围 | 印记有效或拒绝 | 候选副本与已验证副本逐字节相同，套件覆盖候选提供的接口主版本 |
| `SW-3` | 打开副本，读取入口符号，按 `DOC-12` §3 握手，读取描述符 | 新库描述符 `D_new` | ABI 版本受支持；`panic` 策略为 `unwind`；插件名一致 |
| `SW-4` | 接口兼容检查：`L_old` 当前提供且有使用方的每个接口，`D_new` 都提供同一主版本且次版本不低于原值 | 通过或拒绝 | 拒绝时未改变任何运行状态 |
| `SW-5` | 对 `L_old` 的每个实例调用导出器（§5） | 原状态块集合 | 任一导出失败则中止，解除冻结 |
| `SW-6` | 由 `D_new` 构造新组件定义，对每个组件调用内核 `Registry::replace(old, new)` | 被替换的实例列表 | 内核按余效应语义先让依赖方清理，再卸载、重载 |
| `SW-7` | 等待被替换实例与依赖方稳定，时限 `swap_timeout_ms`（默认 30 秒） | 全部 `Active`，或失败 | 失败或超时转 §7 回滚 |
| `SW-8` | 确认期：新实例保持 `Active` 达到 `confirm_ms` | 替换确认 | 确认期内失败转 §7 回滚 |
| `SW-9` | 释放原状态块；`L_old` 的租约归零后记录“旧代码静止”；按 `unload` 策略处理库映像（`ADR-0012`） | 替换报告：`RM-3`、`RM-4`、租约归零耗时 | 报告写入日志与 `status.json` |

步骤 `SW-1`–`SW-4` 保持实例、纪元和服务绑定原状。`SW-5` 进入可逆的写入冻结阶段；导出失败时对已进入导出的实例执行解冻，旧实例继续运行。`SW-6` 开始提交生命周期变化。

### 6.1 进程故障与恢复

进程退出、协议错误或连续超时触发 CP-6：核心撤回该连接提供的服务与效应，依赖方进入 Pending。重启按配置退避，默认起始 500 毫秒、每次翻倍，最多 5 次；耗尽后保留失败状态。恢复的实例继承最近一次成功导出的状态。核心退出时释放插件进程组，宿主在标准输入关闭时退出。

### 6.2 跨进程事件

同步与异步事件保留各自的派发族。远端监听器统一接收异步 callback 通知；需要返回值的插件交互使用服务调用。清理回调使用有截止时间的请求，按内核清理语义等待完成。

## 7 回滚

触发条件，满足任一项：

- `SW-7` 中有被替换实例进入 `Failed`，或在时限内未进入 `Active`；
- `SW-8` 确认期内有被替换实例离开 `Active` 且原因不是依赖缺失。

操作：

1. 用 `L_old` 的组件定义再次调用 `Registry::replace(new, old)`。
2. 旧实例的 `apply` 继承 §5.5 保留的原状态块。
3. 新库按 `SW-9` 的规则静止。
4. 记录回滚原因，`status.json` 中该插件标记为“已回滚”，`.cordis/lib/` 保留被拒副本。`watch` 插件将后续候选与被拒副本完整逐字节比较，内容一致时保持当前状态，内容变化时提交新候选。

回滚本身失败时，该插件的实例停在 `Failed`，其余插件不受影响，日志记录两次失败的原因。

## 8 验证门

### 8.1 契约套件

契约套件是一个插件库。它注入被测接口（例如 `kv@1`），在 `apply` 中执行断言，通过内置接口 `cordis.contract@1` 报告每条断言的结果。套件可以要求被测实现做一次状态导出与继承往返，以验证 §5 的协议。

状态往返采用两个阶段：套件在阶段 0 请求往返并交回 apply，宿主停用套件后导出与重启被测实例，再以阶段 1 挂载套件验证继承结果。`stage`、`request_state_roundtrip` 与最终 `finish` 的接口约定见 ADR-0017。

### 8.2 `cordis verify`

```bash
cordis verify --plugin plugins/libkv_file.dylib --suite contracts/libkv_contract.dylib [--config <被测组件TOML配置文件>]
```

1. `cordis-dev` 固定本次被测库与套件副本，在项目 `target/verify/<序号>` 中生成部署并启动独立核心。
2. 装载被测库和套件库，挂载二者，等待套件报告完成。
3. 输出每条断言的结果与 `RM-5`。
4. 套件明确结束、实际断言数为正且全部通过时，把被测库复制到 `.cordis/verified/<插件名>-<序号>.<扩展名>`，写印记文件 `<被测库文件名>.verified.json`：已验证副本路径、套件插件名与版本、覆盖的接口主版本、逐项断言、断言数和时间。多个套件的结果记录为同一副本下的套件列表。

使用子进程的理由：被测库是尚未验证的原生代码，可能使进程崩溃。

### 8.3 印记的使用

`require_verified = true` 时，`SW-2` 对候选库与印记中的已验证副本执行完整字节比对，并检查套件列表覆盖该库提供的每个接口主版本。运行时在 `.cordis/verified/` 保留作为验证依据的副本。

候选复制后、打开库前确认印记与完整字节；握手后按实际描述符检查接口覆盖。安装单个库时旁置印记随来源复制，同字节安装引用复用时可接收后续取得的真实印记。宿主为已接受的缓存库保存相同印记，分组有状态重启继续对缓存路径执行准入。库副本目录使用目录锁分配单调序号，多个宿主共享目录时接续已有最大序号。

## 9 核心升级与有序退出

核心收到 `SIGTERM` 或 `SIGINT` 时：

1. 关闭管理请求入口，等待已经开始的替换结束或回滚。
2. 对全部实例调用导出器，状态块写入 `state/<实例名>.state`。
3. 释放根纤程，等待全部实例 `Disposed`；`watch` 的清理回调释放文件监视器。
4. 等待全部插件进程组退出并完成回收，随后退出核心。

核心启动时，每个实例的 `apply` 继承 `state/<实例名>.state`，读取后该文件移入 `state/consumed/`。

运行期间按 `checkpoint_ms` 导出实例状态并写入状态目录，默认间隔为 60000 毫秒，`0` 关闭定期检查点。有序退出仍写出最终状态。服务管理器在核心崩溃后重新启动核心，实例继承最近一次检查点；插件宿主通过标准输入关闭感知核心退出，释放所属进程资源（`CP-10`、`CP-11`）。

升级核心的步骤：停止旧核心（上述 1–4），替换核心可执行文件，启动新核心。新核心支持的 ABI 主版本范围覆盖现有插件时，插件不需要重新编译（`ADR-0014`）。

## 10 声明式配置

核心读取 `cordis.toml`。

```toml
requires_core = ">=0.1.0,<0.2.0"

[runtime]
plugin_dir = "plugins"          # 插件库与清单所在目录
state_dir = "state"             # 状态块与插件数据目录
require_verified = false
swap_timeout_ms = 30000
confirm_ms = 10000
export_timeout_ms = 5000
apply_timeout_ms = 30000
cleanup_timeout_ms = 30000
invoke_timeout_ms = 30000
checkpoint_ms = 60000
restart_max = 5
restart_backoff_ms = 500
retired_image_limit = 20
unload = "never"                # never | when-unleased，见 ADR-0012

[instance.store]                 # 实例名 store
plugin = "kv"                    # kv-mem 与 kv-file 的共同插件名
component = "kv-store"           # 组件名
group = "storage"               # 原生宿主分组
config = { path = "kv" }         # 交给组件的配置，以自描述格式编码后传入

[instance.counter]
plugin = "counter"
component = "counter"
config = { interval_ms = 100 }

[instance.watch]
plugin = "watch"
component = "watch"
grants = { "cordis.manage@1" = ["install", "replace", "reload"] }
config = { debounce_ms = 300 }
```

实例可以通过 group 指定原生分组，缺省按逻辑插件分别成组。核心在启动及获得授权的 reload 请求中读取配置；文件变化由 watch 插件观察，经 cordis.manage@1 触发安装、替换或重读，核心按下表调和目标状态。

| 变化 | 运行时的操作 |
|---|---|
| 新增实例条目 | 挂载 |
| 删除实例条目 | 释放该实例 |
| 实例的 `config` 变化 | `Fiber::update` |
| 实例的 `plugin` 或 `component` 变化 | 释放旧实例，挂载新实例，状态不迁移 |
| 实例的 `group`、`isolate` 或 `intercept` 变化 | 在新分组或新视图中重新挂载 |
| `watch` 观察到已有逻辑插件的新构建 | 调用 `install`，然后对对应分组调用 `replace`（§6） |
| 获得授权的 `add` 请求引用新插件 | 在指定分组挂载新增实例 |
| 构建来源文件被删除 | 已装载的副本继续服务，配置或管理请求决定实例的释放 |

这一层就是 `PAPER` §4.2 的组件加载器，它本身由运行时以普通组件的形式挂载在内核上。

配置调和以 `Active` 或依赖缺席时的 `Pending` 作为有效稳定状态。移除提供方会完成依赖方清理并保存新的配置，依赖方在提供方返回后自动激活。执行、清理或截止时间错误仍恢复原部署。普通版本替换沿 `SW-7` 要求受影响实例 `Active`；带完整配置重读的批次使用配置目标的稳定语义（ADR-0044）。

### 10.1 管理授权与持久叠加层

cordis.manage@1 提供 install、add、remove、replace、rollback、configure、reload、shutdown。授权由 cordis.toml 实例条目的 grants 指定，可写具体方法名或 `*`；获得授权的实例取得对应服务，方法调用逐项检查权限。管理接口维持原有授权范围，配置重读从人维护的文件重新取得授权。

管理变更保存到 state/instances.toml，启动时覆盖基础配置中的同名实例；删除操作保留相应持久标记。status 显示覆盖来源。基础 cordis.toml 由人维护，管理操作记录调用方、方法、目标及结果。对调用方自身的 remove、replace 在响应之后执行。

install 的 source 位于项目目录或调用方的数据目录，安装使用单调序号；完整字节相同的内容复用已有插件引用。运行时串行处理管理操作并执行既定验证、时限与回滚规则。调用方的服务可见性和每次方法调用分别由核心检查（ADR-0024）。`replace_batch` 的完整窗口事务及附加重读授权见 ADR-0031。

### 10.2 隔离域与拦截

实例条目的 `isolate` 以接口键为索引，字符串值指定共享的命名域，`true` 创建该实例独有的域。提供方与使用方使用同一个域名时共享该域内的服务绑定。`intercept` 在实例上下文中覆盖相应接口的元数据；声明 `scoped` 的提供方经 `cordis.scope` 为该使用方建立视图对象（DOC-15 §6.4）。

```toml
[instance.tenant-store]
plugin = "kv"
component = "kv-store"
isolate = { "kv@1" = "tenant-a" }
config = { path = "tenant-a.cbor" }

[instance.tenant-counter]
plugin = "counter"
component = "counter"
isolate = { "kv@1" = "tenant-a" }
intercept = { "kv@1" = { namespace = "tenant-a" } }
config = { interval_ms = 100 }
```

这些配置由核心内核派生上下文实现。插件通过 `ctx.isolate`、`ctx.intercept` 与 `ctx.plugin` 使用相同的语义。父实例释放完成时，它创建的子实例和私有域服务均已回收。

逻辑配置组使用 `[scope.<名称>]`，实例通过 `scope` 指定归属，组通过 `parent` 形成继承关系。组的禁用状态、隔离域和拦截元数据传递给成员；组中的 `isolate = true` 使成员共享该组的独有域。实例的 `group` 继续表示宿主进程分组，二者分别对应上下文继承和代码装载（ADR-0033）。

```toml
[scope.tenant]
disabled = false
isolate = { "kv@1" = true }
intercept = { "kv@1" = { namespace = "tenant" } }

[scope.tenant-readers]
parent = "tenant"

[instance.scoped-store]
plugin = "kv"
component = "kv-store"
scope = "tenant"
group = "storage"
config = { path = "tenant.cbor" }

[instance.scoped-counter]
plugin = "counter"
component = "counter"
scope = "tenant-readers"
disabled = false
```

设置组或实例的 `disabled = true` 后，其配置保留，成员从运行目标中移出；重新启用时恢复挂载。配置重读按稳定的实例名比较展开后的目标，变化涉及的条目执行更新或重建，其余实例沿用现有纪元。管理持久化保存成员自身的字段，祖先属性在每次目标展开时合并。

### 10.3 插件清单

原生插件可以直接以动态库文件名作为实例的 `plugin` 引用；目录形式的插件使用 `cordis-plugin.toml` 描述入口。原生清单的名称和版本与宿主读取的动态库描述符一致，`library` 按当前平台补全动态库前缀与扩展名。

```toml
name = "kv"
version = "0.1.0"
socket = "native"
library = "kv_file"
```

进程插件使用 `socket = "process"`，声明 `protocol = 1`、`command` 和可选的 `restart`。原生分组由实例的 `group` 配置决定，进程插件各自运行在独立进程中。

网页插件使用 `socket = "web"`，必需的 `[web]` 声明资源和入口。原生或进程插件追加同一段即可提供浏览器部分。

```toml
name = "dashboard"
version = "0.1.0"
socket = "web"

[web]
assets = "web"
mount = "/dashboard"
entry = "index.js"
```

`assets` 相对插件目录，`entry` 相对 `assets`。HTTP 插件按部署序号发布 `/_cordis/<插件>/<序号>/<入口>`，相对资源引用保留该序号。HTTP 实例配置 `forwarder = true`，核心按实际来源连接与加载上下文授予转发能力。每个页面分别握手并持有独立编号表，其子实例与服务域由核心内核管理（DOC-15 §11、ADR-0041）。

纯网页组件名为插件名；全栈插件的浏览器组件名为后端组件名加 `/web`。两部分共用清单版本及替换事务。替换依次完成后端激活与各页面更新，步骤失败时恢复旧后端和页面状态。资源登记归属对应实例的效应，页面退出回收本页子实例，插件停用撤回资源路由。

### 10.4 上游配置与工具行为对应

| 上游参考 | Rust 配置或工具 | 采用方式与差异依据 |
|---|---|---|
| loader 的 `EntryOptions.id/name/config` | 实例表名、`plugin/component/config` | 稳定实例身份用于增量调和；插件与组件分别选取描述符中的装载单位和入口 |
| loader 的 `group = true`、父上下文继承 | `scope`、`parent` | 逻辑组继承隔离域、元数据和禁用状态；`group` 留给 DOC-15 的宿主进程分组 |
| loader 的布尔 `disabled`、命名或独有 `isolate` | 同名字段 | 采用布尔禁用和上下文域语义；JavaScript 表达式按 Q0 改为数据配置，服务依赖由插件描述符声明 |
| create 的目录准备、模板和启动提示 | `cordis new`、`new-plugin` | 支持新目录与已有空目录；本地模板匹配 Rust SDK，显式命令便于 Cargo 工作流，已有文件保留（ADR-0032） |
| logger-console 的前缀、标签、时间与多行布局 | `console-log` | 保留格式与过滤行为；标准错误承载终端输出，时间以事件接收时刻计算，日期格式采用 strftime（ADR-0032） |
| hmr 的变更合并与替换单元 | `watch` 的完整窗口事务 | 按项目要求覆盖整个防抖窗口；配置与插件候选共同成功或共同恢复，具体上游差异见 ADR-0031 |
