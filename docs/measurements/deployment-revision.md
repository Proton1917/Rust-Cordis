# 部署修订的实现与实测

2026 年 11 月 22 日的对照基线为 `2edc244cae71bd895d55b062fd20c3acd1318cb2`。候选程序来自本次修订工作树的两次 release 构建。五种启动内存场景采用 07:19 UTC 的阶段构建，状态恢复和 64 B 调用采用 09:56 UTC 开始构建的候选。两次测量均在 macOS 27.2 arm64 上进行，基线和候选沿用相同的工作区 `Cargo.lock` 和 Rust 1.96.0 工具链。后一次记录了 14 个逻辑 CPU，以及参与比较的程序名、字节数和修改时间。[测量输入](deployment-revision/workload-inputs.json)

## 实现与职责

| 逻辑职责 | 所有者与本次变化 |
|---|---|
| 部署目标与持久决定 | `cordis-runtime` 的控制器把启动、修改与替换映射为部署目标。`Store` 依据日志标记提交或恢复基础配置、来源和检查点，在线确认与离线查询据此解释有效来源。`cordis-supervisor` 负责根据实际绑定冻结、确认和退役相关实例。 |
| 管理受理与页面 | 运行时管理队列持有受理和执行结果，`cordis.manage@2` 对外提供票据查询。watch 通过该接口提交操作。`cordis-web-deployment` 随所属页面与父效应管理页面实例，在部署事务中交接页面状态。 |
| 状态与原生执行 | 监管器在内存中通过 `Arc<State>` 共享同一版本的检查点与继承状态。宿主在 ABI 边界借用输入解码，清除了独立的取消诊断登记。纯计数、KV 与日志插件的导出声明控制库级 Tokio 环境。 |
| 任务、调用与对象 | 内核执行器取得原任务，纤程复用稳定状态判断。UP/1 将取消责任与请求状态登记在同一条发送路径上，路由目录从活动对象映射求取余额。 |
| 应用交付 | `cordis-dev` 从部署清单定位 Cargo 工作区，按实际包、目标和特性装配产物。部署格式 2 采用新的宿主默认分组，格式 1 沿用历史分组规则。 |

部署决定、状态及资源的定义见[部署规格](../deployment-semantics.md)，构建输入和兼容入口见[运行时与构建职责](../13-runtime-architecture.md)。

## 启动后的内存与线程

每个场景先运行探索对，再交替先后顺序运行十对正式样本。每次使用独立部署目录，周期检查点关闭，确认窗口为 20 ms。程序发布所有实例为 `active` 的第一份状态快照后等待 200 ms，再读取核心和宿主进程的 RSS、Darwin `physical_footprint` 与线程。下表的绝对量为两版各自的十次中位数。变化率逐对计算为 `候选 ÷ 基线 − 1`，方括号列出正式配对最小值和最大值。总足迹是各进程同时段采样值的和，反映本次采样时点。[测量程序](../../benchmarks/deployment/memory.py) · [原始样本](deployment-revision/memory.jsonl)

| 场景 | 宿主数 | 总物理足迹 MiB | 足迹配对变化 | 总 RSS MiB | 线程数 |
|---|---:|---:|---:|---:|---:|
| 空核心 | 0 | 2.06 → 2.08 | +0.38% [−1.51%, +3.08%] | 5.45 → 5.50 | 15 → 15 |
| 一个内存 KV | 1 | 4.60 → 4.45 | −2.91% [−4.39%, −1.37%] | 11.88 → 11.47 | 25 → 24 |
| 四个隔离的内存 KV | 1 | 5.03 → 4.83 | −4.19% [−5.90%, −1.87%] | 12.34 → 11.89 | 28 → 27 |
| KV、计数和日志共享宿主 | 1 | 6.15 → 5.74 | −6.97% [−8.35%, −3.83%] | 21.62 → 20.55 | 30 → 26 |
| KV、计数和日志分别部署 | 3 | 10.17 → 9.74 | −4.51% [−7.13%, −1.70%] | 30.32 → 29.18 | 44 → 41.5 |

空核心变化接近样本波动。四个含插件的场景中，所有正式配对的总物理足迹均下降。首份活动快照的计时包含状态发布间隔，按配对计算的变化在各场景均跨过零点。[原始样本](deployment-revision/memory.jsonl)

## 状态恢复与跨宿主调用

两版各用独立部署目录，关闭周期检查点、确认等待和自动重启。状态场景使用基线真实运行后写出的检查点，1 MiB 和 4 MiB 恢复各十对，逐字节核对继承值。恢复耗时从启动核心计到探针发布核对结果。64 B 场景让同一探针跨宿主读取实际 KV 值，热身 1,000 次后计量 10,000 次读取、复制和释放。吞吐按整个循环的耗时计算，p99 对单次观测采用最近秩法。探索对保留在原始文件中，表中只用正式样本。[实验入口](../../benchmarks/deployment/workload.py) · [原始样本](deployment-revision/workload.jsonl)

| 恢复场景 | 采样总物理足迹 MiB | 核心物理足迹峰值 MiB | KV 宿主物理足迹峰值 MiB | 启动至值核对 ms |
|---|---:|---:|---:|---:|
| 1 MiB | 15.12 → 14.06（−6.72%） | 8.00 → 7.09（−11.07%） | 7.13 → 6.99（−1.77%） | 1,253 → 1,565（+21.19%） |
| 4 MiB | 45.75 → 37.66（−17.65%） | 21.06 → 17.15（−18.61%） | 24.67 → 20.51（−16.86%） | 1,356 → 1,349（+0.06%） |

峰值以各进程独立记录为准。4 MiB 核心峰值的十对变化为 −25.44% 至 −18.16%，宿主峰值为 −17.15% 至 −16.60%。1 MiB 核心峰值为 −12.28% 至 −10.00%，宿主峰值为 −14.37% 至 +19.04%。1 MiB 与 4 MiB 恢复耗时的第 2 至第 9 个排序配对分别为 −17.40% 至 +58.37%、−37.44% 至 +50.62%，两项耗时均待确认。[配对汇总程序](../../benchmarks/deployment/summary.py)

| 64 B 指标 | 基线 → 候选中位数 | 配对变化中位数 | 第 2 至第 9 个排序配对 | 5% 回归带 |
|---|---:|---:|---:|---|
| 吞吐（次/秒） | 7,091 → 7,107 | +0.11% | −0.62% 至 +1.92% | 通过 |
| p99（µs） | 195.06 → 195.71 | +2.56% | −11.51% 至 +9.04% | 待确认 |

5% 判定使用排序后的第 2 和第 9 个变化率作为波动区间。区间宽于 5 个百分点时，性能结果记为待确认。该负载结束时总物理足迹为 8.21 → 8.26 MiB，配对中位数 +0.38%。核心进程峰值为 3.08 → 3.29 MiB，配对中位数 +6.61%，取值 +3.55% 至 +13.47%。这组结果描述本次跨宿主读负载；通用分配次数、默认周期任务、长时换代和 Linux PSS 仍缺对应实测。[原始样本](deployment-revision/workload.jsonl)

## 固定机器入口门槛

固定入口实验在基线宿主内比较同一个计数实现的 ABI 1.2 类型化调用与固定 CBOR 标量调用。各路热身 10,000 次、连续调用 100,000 次，并另测 2,048 个单次延迟样本。十个正式配对中，固定入口的吞吐为基线的 18.68% 至 21.73%，中位数 19.74%，低于 95% 下限。p99 为基线的 2.48 至 3.98 倍，中位数 2.98 倍，高于 1.05 倍上限。该方案在同步标量门槛即终止，当前工作树继续使用 ABI 1.2 与 UP/1。异步、字节、资源和组合业务负载属于该入口的后续独立评估范围。[实验定义](../../benchmarks/direct-call/fixed-entry/README.md) · [逐对结果](deployment-revision/fixed-entry-scalar.json) · [单次延迟样本](deployment-revision/fixed-entry-scalar-raw.json)

## 工作树的跨模块验收

| 入口与条件 | 可观察结果 |
|---|---|
| 同一个部署事务替换后端和网页组件，两个 Chrome 页面各有草稿与计数 | 候选拒绝时票据进入 `restored`，两个页面都能读回共享业务值。成功替换时票据进入 `succeeded`，文档身份、各页草稿和计数保持；配置更新与移除随后成功。 |
| 原程序和恢复来源均失效 | 公开票据为 `recovery_required`，离线查询仍读到原持久决定；后续结构变更受限，隔离分组继续返回业务值。 |
| 八个调用线程跨越五十次原生替换 | 用例完成五十轮与阈值重启。暂停时间中位数 167 ms、最大 756 ms，受理 RPC 中位数 0.247 ms，端到端观察中位数 230.75 ms。这是一次固定换代序列的实测。 |
| UP/1 握手、嵌套调用与旧端兼容 | Rust 双向传输、Python 三项及 Node 两项会话检查通过；新对等端在嵌套调用中扣减父预算。旧核心与新版 watch、旧 watch 与当前核心的兼容用例通过。 |
| 重启流程归并、打包来源单次解析 | 四个监管器故障与重启用例、原恢复来源失效用例通过。同名目标归档和签名后移动验证库两个打包用例通过。工作区 `cargo build --workspace --locked` 成功。 |
| 实例记录与授权共享 | 修订后按当前源码构建运行时和宿主，契约套件在重启后重新挂载并通过。两个页面的联合替换和恢复再次通过，各自的草稿、计数与共享 KV 值保持。 |
| Python 通用编解码 | KV、计数插件在独立部署目录成功加载，独立生成模式的资源用例通过。Python HTTP 插件通过真实路由接收 POST 并返回原来的四个字节。首次装载因生成文件缺少 `Protocol` 导入而失败，修复生成器并重新生成三个官方绑定后取得通过结果。 |

五十轮序列的样本保存在[原生替换记录](deployment-revision/replacement.json)。页面恢复与提交后分别保留了[恢复画面](deployment-revision/batch-restored-1.png)和[提交画面](deployment-revision/batch-accepted-1.png)。上游矩阵共 177 项，8 项直接移植、166 项按 Rust 契约改写、3 项归为不适用。有限参考模型在两份部署、四个持久字段和最多二十步事件的边界内达到不动点，共 22 个可达状态、66 个转换；影响闭包另检查了三节点的 64 种有向边集及 512 种图与起始集合组合。[模型结果](deployment-revision/model.json)

### 解码分配与协商后的性能

| 加载请求中的状态 | 克隆后解码，分配次数／申请字节 | 借用后解码，分配次数／申请字节 |
|---|---:|---:|
| 1 MiB | 29／2,098,561 | 10／1,049,174 |
| 4 MiB | 29／8,390,017 | 10／4,194,902 |

两条路径使用相同的真实 KV 检查点和生产 `from_value`。分配窗口从输入值交给解码器开始，到取得拥有型 `Apply` 结果结束。[分配原始记录](deployment-revision/decoder-allocation.jsonl)

接入剩余时限协商后，以原负载单独重测 64 B RPC。十个配对的吞吐变化中位数为 −2.21%，p99 变化中位数为 −0.69%。按从小到大第 2 至第 9 个配对计算，吞吐比值落在 0.9101–1.0082，p99 比值落在 0.8438–1.4694。两项中位数均在 5% 回归带内，波动越过该带，统计结论为待确认。[协商后逐次样本](deployment-revision/negotiated-rpc.jsonl)

## 生产实现量

基线和工作树使用同一份 `tools/revision_lines.py` 统计物理行。内嵌 Rust 测试按语法树区分，符号链接按其目标文件计一次。下表的生产列单列手写实现；项目汇总另计构建工具、交付模板和生成源码。测试、基准和文档各自归类。[基线分包与职责统计](deployment-revision/size-baseline.json) · [工作树分包与职责统计](deployment-revision/size-candidate.json)

| 生产实现 | 基线 | 工作树 | 净变化 |
|---|---:|---:|---:|
| cordis | 4,933 | 4,909 | −24 |
| cordis-runtime | 5,776 | 5,947 | +171 |
| cordis-supervisor | 6,537 | 6,253 | −284 |
| cordis-host | 3,356 | 3,145 | −211 |
| 四包合计 | 20,602 | 20,254 | −348 |
| cordis-dev | 2,952 | 3,279 | +327 |
| cordis-up | 1,861 | 1,973 | +112 |
| 全部手写生产实现 | 44,781 | 45,146 | +365 |
| 交付模板 | 476 | 291 | −185 |
| 生成源码 | 7,753 | 7,261 | −492 |
| 生产、交付模板与生成源码小计 | 53,010 | 52,698 | −312 |
| 构建与工具 | 722 | 993 | +271 |
| 生产、构建工具、交付模板、生成源码合计 | 53,732 | 53,691 | −41 |

全项目实现量净减 41 行，约 0.08%。四个重点包净减 348 行，约 1.69%。按手写职责分别统计，原生执行减少 210 行，部署减少 112 行，构建前端与打包增加 327 行，进程与协议增加 100 行。Python SDK 现在持有通用编解码，官方 KV、计数与 HTTP 绑定分别保留各自的业务类型和代理，单文件独立生成入口继续内嵌同一实现。这部分代码从交付模板转入 SDK，也消除了每个官方生成件携带的通用实现。单独考核手写生产代码时，结果为增加 365 行，整体降幅亦低于首轮 5%–10% 的规划区间。Linux x86_64 的 PSS 与时延需要在指定主机上取得。
