# 运行时调用与宿主资源测量

本次测量比较提交 `1e65e6498bf97b7a99f6cc1478b716894d1fe137` 与当前分支的运行时实现。测量日期为 2026 年 11 月 23 日，环境为 Linux x86_64、AMD EPYC 9V74、9 个可用逻辑 CPU、Rust 1.96.0 release 构建。源码、执行文件及共享插件的摘要保存在 [source-manifest.json](runtime-efficiency/source-manifest.json) 和各实验的 `inputs.json` 中。

已测场景中的主要收益为：64 B 跨宿主调用的配对中位延迟下降约 27%–29%，配对吞吐提升约 42%–43%；1 MiB、4 MiB 消息运行后的进程总 PSS 下降约 23%–34%；1 万个实例迁入已有 1 万个实例的组件运行时并等待重新稳定，三轮中位耗时由 2045.72 ms 降至 28.02 ms。大消息的吞吐及 P99 存在明显轮间波动，具体范围见下文。

## 调用路径与实现

Rust-cordis 的内核管理组件、依赖绑定、效应和生命周期，部署层管理原生宿主和脚本进程。跨宿主调用经过使用方 SDK/ABI、使用方 host、核心路由、提供方 host，再沿响应路径返回。UP/1 在进程之间传递编码帧，原生插件另有独立执行器。组件语义与宿主工程分层见[组件模型](../00-strategy.md)和[运行时架构](../13-runtime-architecture.md)。

这条调用路径上的参数与结果现在通过所有权转移构造和拆解 DTO，资源编号在原有值树中改写。接收载荷继续保有资源租约，导入完成后才释放。发送方一次生成包含长度前缀的有界帧，并在等待队列容量前释放业务值树，从而缩短大缓冲与编码帧同时存活的时间。兼容形状仍按原有 Serde 规则解析，帧上限和资源提交、回滚约定保持有效。

内核的实例替换利用组件运行时之间实例集合互斥的约束，直接迁移源实例列表；相同规范运行时的替换继续走原有身份分支。清理任务投递失败时，内核在状态锁内维护挂起清理数量。数量为零时，查询和恢复操作直接结束该检查；有挂起清理时继续定位并恢复原有 future。计数更新与槽位写入、取出位于同一临界区，独立失败任务分别恢复的用例覆盖该约束。这两处调整消除了大规模替换中的重复列表与槽位扫描。

宿主主线程推进协议运行时，插件轮询、回调、同步等待和析构继续使用独立原生多线程执行器。每个宿主因此省去两个固定协议工作线程。成功响应、本地计时器和远端超时通过同一 pending 表确定唯一完成方，在该临界区内更新连接连续超时状态，然后在锁外执行通知和关闭。回归用例覆盖成功应答已收到、调用方尚未再次轮询的顺序。

watch 按实际安装副本记录候选内容和拒绝身份。异步安装期间继续变化的源码会在下一次比较时重新判定；同内容拒绝抑制和配置内容比较仍然有效。安装成功的批次直接记录本次返回的副本路径，省去候选记录阶段的全目录内容比较，并释放此前保留的完整运行时快照。

## 跨宿主调用

每组条件执行 1 对预热运行和 5 对正式运行，版本执行顺序逐对交替。两版使用字节完全相同的探针和 KV 提供方，部署结构固定为核心、consumer host、store host。正式测量阶段没有同时运行编译或其他测试。

串行 64 B 每轮 2000 次调用，四路并发每轮共 4000 次；1 MiB 每轮 512 次，4 MiB 每轮 128 次。64 B 预热 200 次，大消息预热 32 次。每次调用计时覆盖返回值释放；四路并发还逐次核对完整返回字节。进程启动、初始写入、预热和并发线程创建位于计时窗口之外。吞吐以总调用数除以测量循环墙钟时间计算。并发模式总时间从统一放行至最后一个线程结束，样本合并和线程回收在窗口之外。

| 1 MiB | 1.090 | 1.282 | 0.978 | 0.245–4.525 |
| 4 MiB | 1.056 | 1.124 | 0.949 | 0.515–1.243 |

双工作线程增加了宿主线程数，在每种载荷的五对观测中各有两对 P99 改善，其余三对回退。当前证据支持保留主线程协议调度，并将尾部波动作为性能适用条件。同步 CBOR 编解码会占用协议调度时间；实验记录的是完整调用时间，各次尾部停顿的操作系统调度、分配器和编解码贡献仍需分阶段观测才能归因。

## 内存与线程

PSS 按共享页面的实际共享比例分摊驻留内存。以下数据在测量报告发布后采样，总计覆盖核心和两个 host；各列分别取五轮中位数。MiB 使用 1048576 字节。

| 并发数 | 载荷 | 总 PSS：基线 → 候选，MiB | consumer host PSS，MiB | store host PSS，MiB | 总 PSS 配对下降 |
|---:|---:|---:|---:|---:|---:|
| 1 | 1 MiB | 50.15 → 32.24 | 18.78 → 10.74 | 13.57 → 12.40 | 26.9% |
| 4 | 1 MiB | 71.77 → 56.96 | 24.97 → 16.90 | 18.61 → 14.48 | 22.7% |
| 1 | 4 MiB | 144.95 → 93.38 | 56.78 → 32.72 | 44.55 → 36.48 | 34.2% |
| 4 | 4 MiB | 191.77 → 130.27 | 80.99 → 52.96 | 60.59 → 40.59 | 29.1% |

以上全部大消息配对的总 PSS 都下降。该指标描述报告发布后的驻留状态；原始数据另存每进程 `VmHWM`，其窗口覆盖启动、准备和测量，各进程峰值发生时间可能不同。

空闲测量在首个完整 Active 快照后等待 200 ms，单独记录预热对和五对正式样本。单 host 的线程数中位数为 8 → 6，三个独立 host 合计为 27 → 19。单 host PSS 为 3.697 → 3.631 MiB，三个 host 合计为 6.103 → 5.898 MiB；空核心 PSS 为 6.34 → 6.41 MiB。空闲内存变化较小，大消息场景的缓冲生命周期调整贡献更明显。短时采样还包括动态创建和缓存的 blocking/native 线程，因此观测线程总数随轮次变化。

### DTO 的分配窗口

同一 release 测试程序交替执行旧 Serde 路径和所有权路径，各做九轮。分配统计窗口覆盖 DTO → 值树 → DTO 的往返，输入创建、最终业务结果释放和 IPC 编解码各有独立边界。

| 4 MiB 业务缓冲 | 分配次数：旧路径 → 所有权路径 | 额外申请字节：旧路径 → 所有权路径 |
|---|---:|---:|
| Invoke 往返 | 11 → 5 | 8389052 → 276 |
| InvokeResult 往返 | 5 → 3 | 8388745 → 137 |

所有权路径复用已有业务缓冲，表中计数反映该转换窗口的额外堆申请。端到端调用仍执行 ABI/CBOR 编解码、进程传输和业务处理，其速度由 RPC 样本报告。[原始分配样本](runtime-efficiency/payload.jsonl) · [分配汇总](runtime-efficiency/payload-summary.json)

## 正确性与复现

选定的内核、协议、路由、监管器、宿主、watch 和 runtime 套件合计 340 项通过，失败为 0。默认忽略的三项为计时入口，其中 DTO 与替换规模入口另以 release 模式执行。`watch_compat` 限定 macOS，本次 Linux 运行选中 0 项。

覆盖场景包括取消后的资源回收、资源租约、乱序轮询下的连续超时统计、投递失败后的独立清理恢复、畸形协议及洪泛、原生 panic/段错误/栈溢出/无限计算隔离、原生工作线程耗尽后的超时回收、替换与回滚、核心 SIGKILL 后恢复、检查点失败和真实 watch 重载。压力入口包括八线程五十次原生替换，以及内核八工作线程一千轮恢复。

跨语言使用实际 Rust、Python、TypeScript 提供方执行三组场景；Python 与 TypeScript 双向传递 `[0,127,255]`，Rust → Python → TypeScript 状态迁移成功，三个提供方各八项接口契约断言全部通过。测试驱动直接使用已安装的 Python 运行时；Conda 包装入口在当前环境缺少 Conda，底层场景、SDK 和夹具保持原样。

普通 Clippy 检查完成，保留四个既有警告：三个既有函数参数数量，以及 `cordis-runtime::Work` 的枚举大小差异。严格零警告门禁仍有这些既有项待处理。修改的 Rust 文件通过 rustfmt 检查，Python 驱动通过语法编译，补丁通过空白检查。[验证摘要](runtime-efficiency/validation/summary.json)与同目录日志记录执行结果。

主要复现入口如下，路径指向预先完成的构建产物，测量期间保持同机其他工作空闲：

```sh
cargo test --locked -p cordis -p cordis-up -p cordis-routing \
  -p cordis-supervisor -p cordis-host -p cordis-watch --no-fail-fast
cargo test --locked -p cordis-runtime --lib \
  --test runtime --test watch --test watch_compat --test stress
cargo test --release --locked -p cordis-up --test payload_performance \
  -- --ignored --nocapture --test-threads=1

python -m benchmarks.deployment.rpc \
  /path/to/baseline /path/to/candidate \
  /path/to/libcordis_latency_probe.so /path/to/libkv_mem.so \
  /path/to/rpc-output --pairs 5 --warmup-pairs 1 \
  --samples 2000 --warmup 200 --large-samples 512 --large-warmup 32 \
  --concurrency 1 --size 64 --size 1048576
```

四路并发使用 `--concurrency 4 --samples 4000`；初始 4 MiB 对照单独使用 `--size 4194304 --large-samples 128`。协议执行器消融对两个大消息均使用 512 次。内核替换在两个源码工作区加入同一测试入口，以 `cargo test --release -p cordis --test replacement_scaling --no-run` 构建，再把两个测试执行文件交给 `python -m benchmarks.deployment.replacement`。内存入口为 `python -m benchmarks.deployment.memory`。完整实参见[测量命令](runtime-efficiency/measurement-commands.json)，驱动摘要见 [driver-hashes.json](runtime-efficiency/driver-hashes.json)。
