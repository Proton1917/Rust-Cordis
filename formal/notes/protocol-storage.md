# Protocol, SDK terminal ownership, and persistence

## Model objects and source boundaries

`Protocol.lean` describes completed UP/1 critical sections and the single writer's queue. `SdkProtocol.lean` describes synchronous response sections on the Python and JavaScript event loops. `Persistence.lean` describes a deployment transaction, durable directory entries, undo replay, and checkpoint-cache confirmation.

The models quantify over arbitrary finite traces and unbounded natural counters. Their transition rules use implementation guards such as a pending entry, a completed file sync, or an empty write plan. Preservation and reachability theorems derive the invariants from initial states. The executable probe separately compares selected production function bodies with finite vectors generated by the Lean definitions.

The machine-readable source mapping is `formal/bridges/protocol-storage.json`. Its commands identify executable checks. Per-run receipts record whether those commands actually passed.

| Domain | Source entry points | Main model result | Implementation evidence |
| --- | --- | --- | --- |
| First write and cancellation | `RequestWrite::cancel`, `write_frames` | One owner of the commit-or-rollback decision; cancellation before a positive write prevents starting | Source mapping and `queued_deadlines` integration tests |
| Reply terminals | `Inner::claim_pending`, `cancel_pending`, `receive_response` | At most one claimant and one health update for each pending request | Source mapping and `rpc_deadlines` integration tests |
| Allocated-byte quotas | `Lease::capacity`, `grow`, `Drop` | Data/control bounds, exact growth charge, exact owner return, reserved controls | Original Rust bodies compiled against Lean vectors |
| Queue order | The shared `mpsc` channel and `write_frames` | Dequeued frames form a prefix of accepted frames | Source mapping and `byte_admission` integration test |
| Script SDK terminals | TypeScript `claimPending`/`response`; Python `_response` | Single settlement and a release owner for each late payload | Original bodies executed against Lean-generated traces |
| Deployment publication | `prepare_deployment`, `commit_prepared`, `sync_decision`, `restore_deployment_files` | Recovery yields the old or new complete image; acknowledgement guarantees the new image | Source mapping and storage fault tests |
| Checkpoint reuse | `checkpoint_entries`, `CheckpointCache::bind` | Every reusable cached fact has file and directory confirmation | Source mapping and checkpoint fault tests |

## First write, terminal ownership, and FIFO

The first-write state contains `started`, `cancelled`, a decision token, and ghost counts for granting the commit decision or returning it to rollback. `positiveWrite` models the first successful nonzero `poll_write` while holding `RequestWrite.state`. The model's token represents the right to make this decision, including a request whose optional callback is absent. It counts ownership transfer; callback execution occurs after the lock is released.

`write_trace_unique_owner` proves that the available token, granted commit rights, and rollback rights sum to one after every trace. Each consumed count is at most one. `cancelled_before_start_never_writes` and `cancel_after_start_keeps_commit_owner` cover the two sides of the lock race. The adapter from Rust critical sections to these events relies on the shared mutex and the writer's first-poll control flow.

The pending-reply model projects the connection onto one fresh request id. A terminal event first removes the pending right, then updates health. `terminal_trace_single_claim` bounds both actions by one. `duplicate_terminal_is_noop` applies to any two terminal events. An inherited timeout leaves the connection's own timeout streak unchanged; a claimed healthy response resets it. The model uses natural arithmetic for the streak, while Rust uses saturating `u32` arithmetic. The ownership results are independent of that numeric representation. The Rust request allocator starts at 1 and uses atomic `fetch_update` with `checked_add(1)`: successful IDs increase through `u64::MAX - 1`, and exhaustion returns error code 8 without changing the frontier. TypeScript uses an increasing `bigint` and Python an increasing arbitrary-precision integer; their wire validators enforce the u64 domain. `WireSemantics.allocated_id_advances_frontier` and `consecutive_allocations_never_reuse` prove the frontier contract, while `Architecture` composes persistent frontiers with stale-callback rejection.

The incoming-request model separates the one-shot cancel sender from the serving task's response right. `cancel_request` consumes the sender with `Option::take`; `serve_request` owns the response after its completion/deadline/cancellation selection. `inbound_trace_has_single_reply_owner` bounds both signal delivery and response attempts by one. `cancellation_preserves_serving_tasks_reply_right` states that signaling cancellation leaves response ownership with that task. The projection starts with one successfully registered incoming request.

The queue state records accepted, consumed, and waiting frame lists. Its invariant is `accepted = consumed ++ waiting`. Both insertion at the tail and removal from the head preserve that equation for arbitrary traces. In the actual writer, the next channel receive occurs after the current frame completes or is skipped. The queue theorem establishes ordering; transport progress, task scheduling, and a peer's eventual processing are environment properties.

The following existing production tests exercise the boundary where these models meet asynchronous I/O:

```sh
cargo test -p cordis-up --test queued_deadlines --test rpc_deadlines --test byte_admission
```

`cancellation_retracts_a_writer_owned_frame_before_its_first_byte` covers cancellation while a writer owns a blocked frame. `a_partly_written_request_keeps_its_frame_and_then_sends_cancel` covers completing a partially written frame before the cancel message. `data_byte_limit_preserves_reserved_controls_and_fifo` covers reserved capacity without queue overtaking.

## Allocated-byte ownership

`Usage` has data and control credits. `Budget` has a normal maximum and a reserved control allowance. For additional capacity `needed`, allocation takes the minimum of `needed` and available normal credits. The remainder requires a privileged lease and sufficient reserved credits. This is the same arithmetic used by `Lease::grow`.

The model proves exact allocation conservation, preservation of both pool bounds, unchanged usage after rejected growth, and unchanged control usage for ordinary frames. The implementation checks that the sum of the two limits fits `usize`; the model and probe apply within that finite-width contract.

The owner model represents each live lease by a list cell. Growth changes one cell and charges exactly its extra credits. Drop removes that cell. `live_owner_is_charged` derives the subtraction precondition from membership in this ownership representation. `dropping_owner_returns_exact_credits` proves that removing a cell returns exactly its data/control charge. `all_owned_traces_are_bounded` combines these facts for all legal allocation/growth/drop traces. The Rust correspondence boundary is that each live `Lease` corresponds to exactly one cell and its destructor consumes that cell once.

`tools/protocol_storage_probe.py` extracts the original `Budget`, `Usage`, `Lease`, `impl Lease`, and `impl Drop for Lease` blocks from `rpc/buffer.rs`. It compiles those blocks with overflow checks enabled. A sequential adapter supplies the `parking_lot::Mutex` lock API using `std::sync::Mutex`; the grow and drop bodies are unchanged. Every vector checks the returned admission decision, resulting pool usage, resulting owner credits, and exact credits remaining after dropping the lease.

`ProtocolProbe.lean` generates 13,824 budget vectors, representing 11,354 distinct inputs. They cover all legal usage/owner combinations for the selected small pool sizes, both privilege values, capacity reduction, exact capacity, one-byte growth, full pools, exhaustion, and selected 32-bit/64-bit numeric boundaries. The model supplies the expected answers. Two injected production-body mutations must disagree with those answers: permitting ordinary frames to consume reserved credits, and failing to charge control bytes. The finite experiment checks correspondence for its inputs; the Lean arithmetic theorems apply to all natural inputs satisfying their stated conditions.

## Python and TypeScript terminals

TypeScript removes the `pending` entry before resolving or rejecting the request. Python leaves its dictionary entry in place until `request` reaches `finally`; `_response` first checks `future.done()`. The `Style` parameter retains these distinct state representations. The invariant equates settlement count with the terminal bit, bounds accepted payloads by settlements, and accounts for each created response payload as accepted or closed on the late-response path.

`every_sdk_trace_has_single_settlement` holds for every event trace in either style. It proves at most one settlement, at most one accepted payload, and exact accounting of late payloads. A separate TypeScript delivery model follows an accepted payload while `Promise.all([sent, completed])` waits for send completion. It proves that the request either returns that payload or closes it on send failure, with at most one of those transfers.

The SDK portion of the executable probe extracts Python's `_response` with the Python AST. It executes the original method using a real `asyncio.Future`. It extracts the original TypeScript `response` and `claimPending` bodies, removes only their typed signatures, and executes them with a real JavaScript `Map`. Parsed-message validation, payload accounting, error constructors, explicit dictionary/map cleanup, and Promise callback counters are documented harness adapters.

The generator enumerates all response/error/cleanup traces of lengths zero through six for both SDK styles: 2,186 traces. Each trace compares dictionary/map membership, terminal state, settlement count, constructed payloads, accepted payloads, and late closes. Removing Python's `future.done()` check and removing TypeScript's pending-entry deletion are required negative controls.

Run both source-body probes with:

```sh
python3 tools/protocol_storage_probe.py --lake /path/to/lake --rustc /path/to/rustc --evidence /tmp/protocol-storage.json
```

The probe also requires Node. `--node` selects its executable. It compiles the two imported model modules into a temporary directory, so it can run independently of a shared Lake build. The receipt identifies extracted functions, adapters, case counts, source digest, and rejected negative controls. Whole request coroutines, CBOR codecs, runtime import tables, callback scheduling, and actual Promise/Future wakeup delivery have separate integration boundaries.

## Deployment publication and crash windows

An `Image` maps pathname identities to exact file contents or absence. Contents are opaque natural identities, with equality representing exact bytes. A write plan is an ordered list of pathname/value changes; `applyWrites` computes its complete result. The before image represents the previous committed deployment. The model covers all names in that plan, including `deployment-base-v1.toml`, overlay, sources, and touched instance state files. The frame condition preserves every unchanged name.

The transition machine retains the following publication boundaries:

| Phase or operation | Persistent fact | Recovery after a crash |
| --- | --- | --- |
| Preparing the backup journal | Target names still have the previous committed image | Previous image |
| Journal and parent directory confirmed | Undo names and old contents are available before target changes start | Replay old image |
| Stage and file sync | The staged new file has complete persistent contents before name publication | Replay old image |
| Publish or remove each target name | Individual directory entries may persist independently | Replay old image |
| Data-directory sync | Every target entry in the complete new image is durable | Undo still chooses the old image |
| Move undo marker to staging | The marker move may persist or be lost before its next directory sync | Either complete old image or complete new image |
| Confirm decision-directory sync | The new image and absence of undo are durable | Complete new image |

`Step.persistName` permits independent persistence of any currently visible name during writing. Each successful data write follows a file-sync step; removal of a name has its own transition. `syncDataDirectory` requires an empty remaining write plan. Moving the decision marker requires the data-synced phase. Acknowledgement requires the marker-moved phase. These are the control-flow guards used by the implementation.

`reachable_invariant` proves that every reachable state retains the remainder of the complete write plan, the unchanged-name frame condition, and the phase-specific durable-image fact. `crash_recovery_is_atomic` then proves that recovery yields exactly the complete old image or the complete new image. `acknowledged_deployment_survives_crash` selects the new image once the final directory sync has succeeded. Before moving the marker, recovery selects the old image.

Recovery is also modeled as individual name restoration. `restore_at` calculates the outcome for each name. `interrupted_recovery_can_restart` proves that replaying the full undo set after any partial replay still restores the original image. Repeated keys and absent-file records are included. Completion of recovery requires successful subsequent I/O; a persistent storage error can keep recovery pending.

The environmental filesystem contract consists of atomic per-name rename, complete file contents after successful file sync, directory-entry persistence after successful directory sync, and exclusive ownership of the target directory while the deployment lock is held. `DirectoryInitialization` derives directory confirmation from the complete successful child-to-ancestor sequence. `StorageProgram` constructs backups from the prior image and proves their coverage and original bytes; `StorageControlFlow` connects the supported source program to its I/O cursor. A previously acknowledged image supplies the durable prior state for the next transaction. Filesystem and device implementations, external writers outside the exclusive-ownership contract, and physical media failure behavior remain operating-environment boundaries.

The existing fault-injection suite provides implementation checks:

```sh
cargo test -p cordis-runtime storage::tests::
```

The cases include publication and marker failures, cleanup failure after commit, failed directory confirmation after moving the marker, and interrupted multi-file restoration. They exercise Rust filesystem operations and injected errors. Their scope is distinct from the abstract machine's quantification over crash traces.

## Checkpoint-cache confirmation

The per-entry cache state distinguishes visible contents, file-confirmed contents, directory-confirmed contents, a provisional candidate, and a reusable entry. Starting a write clears the reusable entry. File sync creates a candidate. Directory sync publishes that candidate for reuse. Failure clears both provisional and reusable facts. Rebinding a directory installs a fresh empty cache state, so facts from an earlier directory cannot be reused.

`cache_trace_preserves_durability` proves that every reusable value equals both the file-confirmed contents and the directory-confirmed contents throughout every event trace. In `checkpoint_entries`, the cache mutex hides provisional entries until the batch directory sync returns. A failed directory sync clears the whole cache. A readable uncached file is file-synced and directory-synced before it becomes reusable, covering a prior publication whose final sync failed.

The source mapping also identifies separate representation obligations: exact state equality, retained-byte accounting and eviction, lock behavior, and detecting directory identity changes. Existing checkpoint tests exercise these properties and the file/directory confirmation failure paths.
