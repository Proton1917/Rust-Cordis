# 验证与部署

## 契约套件

套件本身是原生插件，注入被测接口及 `cordis_sdk::builtin::Contract`。`cordis-contract::Suite` 提供 `check`、`equal`、`stage`、`state_roundtrip`、`finish`。

阶段 0 根据接口约定执行真实操作并报告断言。需要检查迁移时调用 `state_roundtrip()`，随后交回当前 apply。核心停用套件、导出并重启被测实例，再以阶段 1 加载套件。阶段 1 读取继承后的业务值并报告断言，最后调用 `finish()`。

断言的期望值来自接口契约。覆盖写入后读取、覆盖写入、键顺序及需要的错误行为；状态迁移以阶段 0 实际写入的值检查阶段 1。Suite 的 `equal` 会向核心报告真假结果，套件明确完成且全部断言通过才取得印记。

在项目目录运行 `cordis verify`，指定被测动态库与套件库；有配置时通过 `--config` 传入被测组件的 TOML 配置文件。多组件库通过 `--component` 和 `--suite-component` 选择入口。

验证成功后，工具保留 `.cordis/verified/` 中的库副本和原库旁的 `.verified.json`。启用 `require_verified` 后，候选与验证副本按完整字节比较，接口覆盖按提供方描述符检查。分发该版本时一起保留验证印记及其引用的副本。

## 开发时替换

在生成项目中执行 `cargo build --target-dir target`，watch 会观察本地构建产物。一个防抖窗口中的候选及配置修改属于一个批次。管理接口返回 `BatchTicket` 表示受理，实际完成状态由 `RuntimeSnapshot.last_batch` 给出；watch 已持久化待确认窗口，可在自身被替换后接续观察。

检查新的版本、实例状态和业务输出，确认依赖使用方已重建。失败时查看实例错误、批次结果与日志；先修复产生失败的配置或代码，再提交新内容。

`cordis status` 读取每 100 ms 发布一次的 `status.json`，管理响应到达时文件可能仍是上一帧。调用结果以管理响应为准；观察文件时，等待本次操作对应的批次编号或替换报告以及实例状态。例如验证回滚，需要同时观察目标插件的 `rolled_back = true` 报告和使用方 `Active`，使断言对应已完成的这一轮操作。

## 迁移既有 Rust 代码

按明确的功能接口划分插件，公共数据类型进入接口 crate。把一次运行所需资源移入 `apply`，把关闭和回退动作登记为效应。把持续任务交给上下文，把持久文件归属数据目录，把跨版本业务数据定义为带版本的状态模式。保持其他插件依赖稳定接口，使实现可以独立替换。
