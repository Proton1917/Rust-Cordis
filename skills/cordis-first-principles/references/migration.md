# 把现有应用迁到 Rust-cordis

本篇适用于已有应用改为在 Rust-cordis 上运行的情况：自研插件系统、单体后端、一组脚本加守护进程，任何语言都算。原版 cordis 或 Koishi 插件不在此列。替换插件时的业务状态迁移是另一件事，见[资源与状态](resources-state.md)“状态迁移”。推论编号见[推论详解](principles.md)。

## 迁移是重新归位，不是搬代码

旧系统的每一项职责，先问：**在新系统里，决定这件事正确结果的事实由谁唯一掌握？** 答案只有三种去处：

| 去处 | 判定 | 旧系统中的典型对象 |
|---|---|---|
| 删除，由核心接管 | 事实是实例、依赖、加载与清理时机、替换与回滚（1.1） | 自研插件加载器、插件清单、服务注册表、依赖排序、热重载、看门狗重启、启动顺序脚本 |
| 交给官方插件 | 事实是协议、机密或文件变化（1.2、2.3） | 自己监听端口的 HTTP 服务器 → http 插件；`.env` 与环境变量中的密钥 → secrets 插件；文件监视触发重载 → watch 插件 |
| 写成业务插件 | 事实是业务数据、领域规则、业务状态（1.3） | 任务队列、调度策略、模型调用、计费、外部 API 客户端；每类事实一个插件 |

旧系统里第一类代码往往最多，也最容易被原样搬进来；迁移完成后，这一类代码应当全部消失。旧目录结构是历史形成的，按事实拆分插件，不按目录拆。

## 旧写法与新写法

| 旧写法 | 新写法 | 依据 |
|---|---|---|
| 插件框架、注册表、启动顺序、重载逻辑 | 删除；每个功能一个 cordis 组件，依赖写进 inject | 1.1 |
| 多个模块共用一个数据库，互相查表 | 按表的所有者拆开，其他模块改为调用所有者的接口；不做让各插件继续共用旧库的通用 SQL 插件 | 2.1、4.2 |
| 自己监听端口、自己解析 Cookie | http 插件的处理方 | 1.2 |
| `.env`、环境变量或配置中的密钥 | 部署系统写入密钥文件（属主为运行用户，权限至多 0600），配置只写键名，经 secrets 服务读取 | 2.3 |
| 参数里传调用者身份 | `caller(metadata)`；终端用户身份由 HTTP 处理方认证后作为业务参数传递 | 2.2 |
| 启动时初始化全局单例、连接池、客户端 | 在 apply 的效应中创建，清理登记在同一效应 | 3 |
| 模块级全局可变业务状态 | 声明状态模式，经导出器迁移；纯缓存可留在 static | 3、4.4 |
| 后台线程、定时器、`setInterval`、裸 `asyncio.create_task`、全局 `tokio::spawn` | Rust `ctx.spawn` / `ctx.spawn_thread`，Python 与 TypeScript `context.task`；定时用任务内的循环 | 3 |
| 进程退出钩子、`atexit`、信号处理 | 效应清理 | 3 |
| 请求处理中同步等待外部服务或模型 | 提交、执行、查询三步（见[调用、超时与长任务](calls.md)） | 3 |
| 同步函数里 `block_on` 等待异步调用 | 方法声明为异步；阻塞库放进 `ctx.spawn_thread` | 3 |
| 启动时读取全局配置文件 | 组件 Config，在 resolve 中检查 | 1.1 |
| 当前工作目录或固定路径下的数据文件 | Rust 用 `ctx.data_dir()`；Python 与 TypeScript SDK 目前没有对应入口，持久路径写进组件配置 | 2.1 |
| 进程内直接调用另一个模块的函数 | 注入对方的版本化接口 | 4.1 |
| 事件总线上需要返回值的“请求” | 服务方法；跨进程事件只是通知 | 4.3 |
| 写在代码里的“A 和 B 在同一进程” | `cordis.toml` 的 `group` | 1.5 |
| 远程 worker 直连内部服务 | worker 经业务插件提供的 HTTP 接口领取任务、提交结果 | 4.3 |

迁移中觉得“必须改核心”时，对照[推论详解](principles.md)“不改内核”一节的常见误判。

## 迁移步骤

1. **盘点。** 列出旧系统的每项职责，填写归位表：职责、决定它的事实、掌握者、旧位置、新去处、接口。验证：每一行都有去处；标为“删除”的行，能说出由核心的哪项机制接管。
2. **定接口。** 先写使用方需要的接口与版本，再写实现。验证：`cordis idl gen` 生成各语言绑定，或 Rust 接口 crate 能编译。
3. **建项目。** `cordis new` 生成项目，配置需要的官方插件（http、secrets、watch）。默认生成的项目以公开仓库地址加固定修订（`git` 与 `rev`）依赖 Rust-cordis，保持这种写法；`--sdk-path` 只用于开发 Rust-cordis 本身。
4. **逐项迁移。** 一次只迁一项职责。每项完成后：`cordis status` 中实例为 Active；用契约套件或真实请求验证；在请求进行中替换一次，确认资源被清理、状态被继承。
5. **新旧并存（需要时）。** 旧系统可以作为外部服务继续运行，由一个适配插件经旧系统自己的网络接口调用它，旧接口逐步由新插件取代。旧框架本身不搬进来。
6. **删除旧框架。** 删除旧的加载器、插件清单、旧 SDK、启动脚本与环境变量文件。验证：仓库中检索旧框架的入口名与清单文件名，没有剩余引用。
7. **发布。** 见[打包](packaging.md)与[生产部署与运维](deployment.md)“首次上线检查”。

## 完成标志

“插件都迁过来、能启动”不等于迁移完成（2.4）。完成以业务结果为准：

- 归位表的每一行都已迁移，并有对应的验证记录。
- 旧系统的每一项用户可见的业务功能，都在新系统中用真实流程端到端走通一次，结果与旧系统一致，或差异已记录。旧系统本来就没有的功能单独列为新工作。
- 关键流程在并发请求下走通，并经历过一次运行中替换。
- 按[推论详解](principles.md)末尾的清单自查通过。
- 没有修改或分叉 Rust-cordis 核心。
