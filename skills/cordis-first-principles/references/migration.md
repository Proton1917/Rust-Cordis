# 把现有应用迁到 Rust-cordis

本篇适用于已有应用改为在 Rust-cordis 上运行的情况：自研插件系统、单体后端、一组脚本加守护进程，任何语言都算。原版 cordis 或 Koishi 插件不在此列（见 SKILL.md“先确认”第 2 条）。替换插件时的业务状态迁移是另一件事，见[资源与状态](resources-state.md)“状态迁移”。

## 迁移是重新归位，不是搬代码

旧系统的每一项职责，先问 SKILL.md 的那个问题：**在新系统里，决定这件事正确结果的事实由谁唯一掌握？** 答案只有三种去处：

| 去处 | 判定 | 旧系统中的典型对象 |
|---|---|---|
| 删除，由核心接管 | 事实是实例、依赖、加载与清理时机、替换与回滚 | 自研插件加载器、插件清单、服务注册表、依赖排序、热重载、看门狗重启、启动顺序脚本 |
| 交给官方插件 | 事实是协议、机密或文件变化 | 自己监听端口的 HTTP 服务器 → http 插件；`.env` 与环境变量中的密钥 → secrets 插件；文件监视触发重载 → watch 插件 |
| 写成业务插件 | 事实是业务数据、领域规则、业务状态 | 任务队列、调度策略、模型调用、存储、计费、外部 API 客户端 |

旧系统里第一类代码往往最多，也最容易被原样搬进来。迁移完成后，这一类代码应当全部消失。

## 规则

每条给出常见的错误写法和正确写法。

**M-1 不在插件里再造内核。** 旧框架整体删除，不包装成一个 cordis 插件继续使用。迁移后的代码里不应出现以下任何一项：
- 按名字查找并加载模块的表；
- 自己维护的“依赖已就绪”标志或启动顺序；
- 自己写的重启、重载、回滚逻辑；
- 全局服务注册字典。

错误：把旧插件框架写成一个 cordis 插件，旧插件继续在它里面注册和互相查找。
正确：旧框架中的每个插件成为一个 cordis 组件，依赖写进 inject，服务写进 provides，由核心调度加载与替换。

**M-2 按事实拆插件，不按旧目录拆。** 旧目录结构是历史形成的。
- 一个旧模块持有两类互不相关的事实时，拆成两个插件；
- 多个旧模块共同维护一类事实时，合并成一个插件；
- 接口按使用方需要的能力定义，带版本（`jobs@1.0`），用 WIT 或共享 Rust 接口 crate 管理。

**M-3 旧的生命周期写法逐项改写，不保留全局初始化。**

| 旧写法 | 新写法 |
|---|---|
| 启动时初始化全局单例、连接池、客户端 | 在 apply 的效应中创建，清理登记在同一效应 |
| 模块级的全局可变业务状态 | 声明状态模式，经导出器迁移；纯缓存可留在 static |
| 后台线程、定时器、`setInterval`、裸 `asyncio.create_task`、全局 `tokio::spawn` | Rust `ctx.spawn` / `ctx.spawn_thread`，Python 与 TypeScript `context.task`；定时用任务内的循环加 `ctx.sleep` |
| 进程退出钩子、`atexit`、信号处理 | 效应清理 |
| 启动时读取全局配置文件 | 组件的 Config，在 resolve 中检查 |
| 事件总线上需要返回值的“请求” | 服务方法；跨进程事件只是通知 |
| 当前工作目录或固定路径下的数据文件 | Rust 用 `ctx.data_dir()`；Python 与 TypeScript SDK 目前没有对应入口，持久路径写进组件配置，不依赖进程当前目录 |
| 进程内直接调用另一个模块的函数 | 注入对方的接口；同组原生插件直接调用，跨进程经 invoke |
| 请求处理中同步等待外部服务或模型返回 | 提交、执行、查询三步；服务方法不等待长工作，见[调用、超时与长任务](calls.md) |

**M-4 协议归终结它的插件。** 核心不监听网络。
- 错误：业务插件自己开一个端口提供 HTTP；或者期望核心解析 Cookie、校验令牌。
- 正确：业务插件作为 http 插件的处理方登记路由前缀（`cordis new-plugin api --rust --http`）。Cookie、会话、令牌校验写在处理方，见 [HTTP](http.md)。

**M-5 机密迁入 secrets 服务，迁移期间也不例外。**
- 错误：先把密钥放进环境变量或插件配置，“以后再改”。
- 正确：部署系统写入密钥文件（属主为运行用户，权限至多 0600），插件配置只写键名，secrets 插件的 `grants` 授权给需要的实例，插件经 `cordis.secrets@1.0` 读取。

**M-6 身份来自核心，登录结果来自处理方。**
- 插件之间的调用方身份用 `caller(metadata)`，不用参数里自报的实例名或用户名。
- 终端用户是谁，是 HTTP 处理方的认证结果，由处理方负责，再作为业务参数传给下游插件。

**M-7 进程划分是部署决定。**
- 旧系统里“A 和 B 在同一进程”不写进代码，改由 `cordis.toml` 的 `group` 决定。
- 原来同进程内的同步调用，拆到不同进程后改为异步服务调用。
- 按故障域分组：调用外部网络、可能长时间阻塞或可能崩溃的插件放进独立分组，不与核心业务共享宿主进程。分组与容量的取舍见[生产部署与运维](deployment.md)。

**M-8 跨机器协作经业务插件自己的网络接口。** 旧系统的远程 worker 改为：业务插件经 http 提供领取任务、提交结果的接口，worker 作为客户端调用，认证由该插件定义。不要求核心之间组网。

**M-9 觉得“必须改核心”时，先对照下表。** 迁移中最常见的误判：

| 以为需要核心做的事 | 实际掌握者与做法 |
|---|---|
| 排队、调度、重试任务 | 业务插件，提供任务接口 |
| 校验登录、维护会话 | http 处理方 |
| 把密钥注入插件进程 | secrets 服务按实例授权读取 |
| 判断请求来自哪个实例或页面 | 已有：`caller(metadata)` 的 `instance` 或 `page_of` |
| 定时触发 | 插件内的任务循环 |
| 运行中装载、替换别的插件 | 已有：持有 `cordis.manage@1` 授权的插件发起 |
| 插件之间共享大块数据 | 字节流对象或资源对象作为参数转交 |

表中没有的，按 SKILL.md“不改内核”四步处理：只有能证明相关事实只有核心掌握时，才写成通用能力交 Rust-cordis 维护者评审，不在自己的项目里修改或分叉核心。

## 迁移步骤

1. **盘点。** 输入：旧系统源码与部署脚本。操作：列出每项职责，填写归位表（职责、决定它的事实、旧位置、新去处、接口）。输出：归位表。验证：每一行都有去处；标为“删除”的行，能说出由核心的哪项机制接管。
2. **定接口。** 先写使用方需要的接口与版本，再写实现。验证：`cordis idl gen` 生成各语言绑定，或 Rust 接口 crate 能编译。
3. **建项目。** `cordis new` 生成项目，配置需要的官方插件（http、secrets、watch）。默认生成的项目以公开仓库地址加固定修订（`git` 与 `rev`）依赖 Rust-cordis，保持这种写法，不改成 `path` 或 `file://`。`--sdk-path` 生成本机路径依赖，只用于开发 Rust-cordis 本身。
4. **逐项迁移。** 一次只迁一项职责。每项完成后：`cordis run` 启动，`cordis status` 中实例为 Active；用契约套件（`cordis verify`）或真实请求验证行为；替换一次，确认资源被清理、状态被继承。
5. **新旧并存（需要时）。** 迁移期间旧系统可以作为外部服务继续运行，由一个适配插件经旧系统自己的网络接口调用它，旧接口逐步由新插件取代。旧框架本身不搬进来。
6. **删除旧框架。** 删除旧的加载器、插件清单、旧 SDK、启动脚本与环境变量文件。验证：在仓库中检索旧框架的入口名与清单文件名，没有剩余引用。
7. **发布。** `cordis pack` 打包，见[打包](packaging.md)。从一个新目录解包，启动，走通关键业务流程，再确认有序退出；按完整字节检查发布物中没有本机用户名与 HOME 路径。

## 完成标志

- 旧框架的加载器、清单、SDK、启动脚本已删除，代码中没有自建的注册表、依赖判断或重载逻辑（M-1）。
- 每个插件持有一类事实，接口带版本（M-2）。
- 没有脱离实例的线程、任务、定时器（M-3）。
- 业务插件不自己监听端口；密钥只以键名出现在配置中（M-4、M-5）。
- 对 Rust-cordis 的依赖是公开仓库地址加固定修订。
- 发布包在新目录启动后，关键流程走通，并能有序退出；发布物不含本机路径。
- 没有修改或分叉 Rust-cordis 核心；迁移中提出的核心需求，已按通用能力交维护者评审，或经 M-9 改为插件实现。
