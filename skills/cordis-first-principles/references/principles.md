# 推论详解

Rust-cordis 的每个设计都先回答一个问题：**决定这件事正确结果的事实，由谁唯一掌握？** 掌握事实的一方承担这项职责。SKILL.md 的掌握者表列出了常见事实的掌握者；本篇展开由此得出的四条推论，每项后果给出错误写法与正确写法，最后是“不改内核”的步骤、遇到没写到的情况的做法，以及交付前自查清单。

Rust-cordis 维护者使用的六条判据（`Q0` 核心不运行插件代码、单一内核、核心之外一切皆插件、协议归终结者、复用与通用、机密不透明），是这四条推论在核心上的应用，不另立规则。

## 推论 1：职责跟着事实走

掌握事实的一方承担职责，其他方向它要，不复制，不代办。

**1.1 核心的事实只由核心决定。** 实例、依赖、加载与清理时机、替换与回滚只由内核决定。
- 错误：在插件里维护模块注册表、“依赖已就绪”标志、启动顺序、重启或重载逻辑；把旧系统的插件框架包成一个 cordis 插件继续使用。
- 正确：每个功能是一个 cordis 组件，依赖写进 inject，服务写进 provides，由核心调度加载与替换。

**1.2 协议由终结它的插件处理。** 谁解析协议，谁负责它的语义；核心只转交不透明数据。
- 错误：业务插件自己监听端口；把 Cookie 或令牌放进 UP/1 元数据，期望核心校验。
- 正确：业务插件作为 http 插件的处理方登记路由，在处理方中校验请求头；页面连接的请求头快照经 `cordis.http-page@1.0` 查询（见 [HTTP](http.md)）。

**1.3 插件按事实划分。** 一个插件持有一类事实；接口按使用方需要的能力划分。一个插件同时持有两类互不相关的状态时，替换其中一类会连带重启另一类；多个插件共同维护一类事实时，没有人对它负责。

**1.4 不为单个使用方开特例。** 某个使用方的需求是它自己的事实，放进核心或共享接口，就放进了不掌握它的地方。
- 错误：为某个应用的任务调度，要求核心增加“按订单排队”的接口；为一个慢方法调大影响所有插件的 `invoke_timeout_ms`；为某个使用方另开一个接口版本。
- 正确：任务队列写成提供 `jobs@1` 服务的业务插件；慢方法在该插件内改为长任务（见[调用、超时与长任务](calls.md)）；数据结构新增字段给缺省值并提升次版本。

**1.5 部署事实不写进代码。** 插件运行在哪个进程、和谁合组、全局超时与重启参数，由 `cordis.toml` 决定。同一份插件可以换组而不改源码（见[生产部署与运维](deployment.md)）。

## 推论 2：只写自己掌握的事实，只信掌握者给出的事实

一项事实只有一个写入者；读的一方从掌握者那里取，不自己伪造、复制或猜测。

**2.1 数据只由它的所有者读写。** 每张表、每个数据文件只属于一个插件，其他插件经它的服务接口访问。
- 错误：做一个通用 SQL 存储插件，多个业务插件把表建在同一个库里，互相直接读写；A 插件为了省事直接查询 B 插件的表。
- 正确：每个插件使用自己的数据目录或独占的数据库。确实需要通用存储插件时，它按 `caller(metadata)` 给出的调用方实例隔离命名空间，一个实例只能访问自己的命名空间，不接受调用方自报的命名空间。
- 原因：同一事实有多个写入方时，出错无法判断谁对；共享表结构还是没有版本的契约（推论 4）。

**2.2 身份只信核心给的。** 一次调用来自哪个实例或页面，只有核心知道。
- 错误：接口参数带 `caller: String`，提供方据此放行。
- 正确：提供方以 scoped 方式提供服务，从 `caller(metadata)` 读取直接调用方：后端为 `instance`，页面为 `page_of`，页面需要显式按 `page_of` 授权。终端用户是谁，是 HTTP 处理方的认证结果，由处理方作为业务参数传给下游。

**2.3 机密与本机信息不复制出去。** 机密的值由 secrets 插件掌握；本机用户名与路径属于这台机器，不属于发布物。
- 错误：在配置里写 `api_key = "..."`，或在启动脚本中 `export API_KEY=...`；日志、错误信息、导出状态或接口返回值中出现机密原文；依赖写成 `file://` 本机路径；发布包里带 `/Users/...`。
- 正确：配置写 `api_key_secret = "MY_KEY"`，secrets 插件的 `grants` 把 `MY_KEY` 授权给需要的实例，插件运行时经 `cordis.secrets@1.0` 读取。依赖写公开仓库地址加固定修订；发布物按完整字节检查（见[打包](packaging.md)）。

**2.4 结论由产生它的过程给出。**
- 错误：测试里直接把“已覆盖”“已批准”“已完成”设为真，再验证后续流程；以“插件都能启动”宣布迁移或功能完成。
- 正确：被测事实由被测代码产生；“完成”以真实业务流程端到端的实际结果为准。

**2.5 Rust-cordis 如何运行，以源码为准。** 调用截止时间、执行线程数、替换时在途调用的处理，都由 Rust-cordis 的实现决定。不确定时到公开仓库（https://github.com/Proton1917/Rust-Cordis）的源码与 `docs/` 中查证，不凭其他框架的经验推断。

## 推论 3：只占用自己拥有的资源，用完归还

每种资源都有主人。占用别人的资源，或者用完不还，就会在替换、并发或故障时出问题。

| 资源 | 主人 | 后果 |
|---|---|---|
| 文件、连接、监听器、后台任务 | 取得它的实例 | 在效应中取得，在同一效应清理；后台工作用 SDK 任务入口（Rust `ctx.spawn` / `ctx.spawn_thread`，Python 与 TypeScript `context.task`），不用全局 `tokio::spawn`、裸 `asyncio.create_task`、`setInterval`（见[资源与状态](resources-state.md)） |
| 调用的截止时间 | 核心（缺省 30 秒，连续 3 次超时终止进程） | 服务方法不等待长工作；长工作改为提交、执行、查询 |
| 原生执行线程 | 宿主（每组缺省 2 个） | 不自己 `block_on`；同步上下文中经宿主的 `context.wait` 等待，异步上下文中 `.await`；阻塞库放进 `ctx.spawn_thread` |
| Python、TypeScript 的事件循环 | 整个进程 | 不做同步阻塞 I/O |
| 本地锁 | 当前代码段 | 调用服务或派发事件前释放，让重入的回调能执行 |

截止时间、执行线程与事件循环的完整事实和写法见[调用、超时与长任务](calls.md)。

## 推论 4：跨越边界只靠带版本的契约

插件之间、进程之间、机器之间，只有写明版本的契约可以依赖。

**4.1 接口带版本。** 公开接口用 WIT 或共享 Rust 接口 crate 管理。次版本只追加方法和带缺省值的字段；不兼容修改发布新主版本（见[接口版本与升级](versioning.md)）。

**4.2 不使用没有版本的契约。** 共享的表结构、全局变量、私有文件格式、日志文本解析，都是没有版本的契约，任何一方改动都会让另一方出错，且插件无法独立替换。

**4.3 跨进程、跨机器只有异步契约。**
- 跨进程事件只是通知，不等返回值；需要回答时用服务方法。同步共享内存与闭包只在同一进程内成立。
- 一个核心只管理一台机器上的插件进程，核心之间不组网。另一台机器上的执行端通过业务插件提供的 HTTP 接口领取任务、提交结果，接口与认证由该插件定义。

**4.4 业务状态带模式与版本。** 跨替换保留的状态声明模式名与版本范围，经导出器迁移；状态版本与接口版本相互独立。

**4.5 动态调用只用于名称确实来自外部的情况。** 方法名来自配置或外部输入时才用动态调用；否则用类型化接口，让版本检查生效（见[按名称调用](dynamic.md)）。

## 不改内核

觉得“这个功能得改核心才能做”时，按顺序走：

1. 用开头的问题找出事实的掌握者。几乎所有情况下答案都是某个插件。
2. 找已有机制：效应、依赖注入、`scoped` 与 `intercept` 元数据、资源对象作为参数转交、动态调用、`cordis.manage@1` 授权、http 路由、secrets 服务。
3. 用插件实现。需要别的插件配合时，定义一个带版本的接口。
4. 只有能证明相关事实只有核心掌握（例如“一次调用来自哪个连接”）时，才把需求写成通用能力，交给 Rust-cordis 维护者评审；不要在自己的项目里修改或分叉核心。

常见误判：

| 以为需要核心做的事 | 实际掌握者与做法 |
|---|---|
| 排队、调度、重试任务；定时触发 | 业务插件的任务接口与任务循环 |
| 校验登录、维护会话 | http 处理方 |
| 把密钥注入插件进程 | secrets 服务按实例授权读取 |
| 判断请求来自哪个实例或页面 | 已有：`caller(metadata)` |
| 运行中装载、替换别的插件 | 已有：持有 `cordis.manage@1` 授权的插件 |
| 插件之间传递大块数据 | 字节流对象或资源对象作为参数转交 |
| 让多个插件共用数据 | 不需要核心：数据归一个所有者，其他插件经接口访问 |

## 本技能没写到的情况

实际出错几乎都发生在没写到的地方：读者按普通后端的习惯处理，例如共用一个数据库、在请求里同步等待几分钟、在同步函数里 `block_on`。遇到这种情况，不要套用习惯：

1. **找事实。** 写下这件事涉及的数据、身份、协议、时间、线程、进程，确定每项事实的唯一掌握者。
2. **查清运行时的真实行为**（2.5）。本技能里的截止时间、执行线程数、连续超时终止，都是这样从源码查出来的。
3. **用四条推论推出做法。** 需要核心增加职责的，回到“不改内核”。
4. **在并发和替换下验证。** 单人、单次的测试发现不了线程耗尽、共享数据冲突、替换时丢任务。至少同时发起几个请求，并在请求进行中替换一次插件。
5. **把结论交回。** 写清事实、来源（源码位置）和推出的做法，交给 Rust-cordis 维护者补进本技能。

## 交付前自查

- 推论 1：每项新增职责能说出它依据的事实由谁掌握；没有自建注册表、依赖判断或重载逻辑；没有为单个使用方开的特例接口、配置分支或全局参数调整。
- 推论 2：没有插件读写别的插件的表或数据文件；授权依据 `caller(metadata)`；机密只以键名出现，日志、错误信息与导出状态中没有机密和业务载荷原文；依赖与发布物中没有本机路径；测试不伪造被测结论。
- 推论 3：资源与后台任务都归属实例并登记清理；清理先发停止信号、所有等待有上限，有序退出在数秒内完成；没有可能超过截止时间的服务方法；Rust 中没有自行 `block_on`，Python 与 TypeScript 中没有同步阻塞 I/O；调用外部前已释放本地锁。
- 推论 4：跨插件交互都经带版本的接口；没有共享表或私有格式；跨进程事件只作通知；状态声明了模式与版本。
- 在并发和替换下验证过。
