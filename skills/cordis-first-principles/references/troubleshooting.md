# 常见故障

先用 `cordis status` 找到失败或 Pending 的实例及其错误，再对照下表。推论编号见[推论详解](principles.md)。

| 现象 | 常见原因 | 处理 |
|---|---|---|
| 实例一直 Pending | 必需依赖没有提供方，或 inject 的接口名、主版本与提供方 provides 不一致 | `cordis status` 查看缺少的接口；核对两边的接口字符串 |
| 取服务时报未声明依赖 | 取用的接口不在 inject 中 | 补声明；Rust 动态名用 `Inject::with_name` |
| 写入返回错误码 4（导出期间冻结） | 替换或检查点正在导出状态 | 请求式写入把错误交给调用方；后台循环等下一轮再写 |
| 替换后旧逻辑仍在执行 | 任务或线程没有归属实例 | 推论 3：改用 SDK 任务入口 |
| `.cordis/lib` 随启动和替换持续增长 | 旧宿主保留工作副本，或仍有活动/重启计划租约；回收错误见宿主诊断 | 推论 3：配套升级支持文件租约的核心与宿主；历史副本按[部署](deployment.md)中的停机和打开文件查询条件清理，备份排除工作副本 |
| 调用返回错误码 6，随后提供方被终止、依赖方转 Pending | 服务方法等待了长工作；Rust 中自行 `block_on`（宿主 stderr 会报告分组的执行线程被占满）；Python、TypeScript 中阻塞了事件循环 | 推论 3，见[调用、超时与长任务](calls.md) |
| 只在并发时出现超时或卡死 | 执行线程或事件循环被阻塞等待占满 | 同上；按[推论详解](principles.md)“本技能没写到的情况”第 4 步做并发验证 |
| 替换、配置更新或其他插件重启后，同一操作执行了两次，出现重复记录或冲突 | 依赖方重建让 apply 再次执行，apply 中触发的提交或写入不幂等 | 推论 1.1：用固定请求键或持久记录判断是否已做过 |
| 有序退出、替换或重启每次都停顿十几秒以上 | 某个效应清理在等待不会自行结束的线程或任务：无超时的条件变量等待、阻塞读、不检查取消的长任务；清理时限只是上限，等到上限才结束 | 推论 3：清理先发停止信号，所有等待设上限并检查 `is_current`，长任务检查取消标志；不要靠放宽时限解决 |
| 事件回调或服务调用卡住 | 持有本地锁时调用服务或派发事件 | 推论 3：先释放锁 |
| 改了一个插件的数据结构，另一个插件出错 | 两个插件共用了表或私有格式 | 推论 2、4：数据归一个所有者，经接口访问 |
| 一个原生插件 panic，整个分组退出 | Cargo profile 设置了 `panic = "abort"` | 使用 `panic = "unwind"` |
| 替换后状态丢失或回滚 | 未声明状态模式，或继承时模式名、版本核对失败 | 核对 state 声明与 apply 中的继承检查 |
| 插件反复重启后停在失败状态 | 进程崩溃，重启次数已耗尽 | 看日志修复原因，见[生产部署与运维](deployment.md)“崩溃与恢复” |
| Python 插件 `ModuleNotFoundError` | 依赖没有装进插件的 `.dependencies` | 按 [Python 插件](python.md) 安装 |
| 跨进程调用返回错误码 8（超出协议预算） | 单次参数或返回值超过 UP/1 限额（缺省 `max_frame` 16 MiB、`max_values` 262,144 个值节点或嵌套深度上限） | 推论 4：大清单、文件或二进制内容改用 `cordis.byte-stream@1.0`、分页或持久引用，RPC 只传小参数和小回执 |
| `cordis-host` 内存或线程数持续偏高 | 多宿主未合组（格式 1）；不需要第三方 Tokio 的插件未写 `tokio = false`；大载荷经 RPC 顶高分配器水位；热替换累积退役 `.dylib` 未触达重启阈值 | 升级到 `format_version = 2` 共享 `native` 组；纯逻辑插件设置 `tokio = false`；大载荷改走流；调低 `retired_image_limit`（见[生产部署与运维](deployment.md#分组与容量)） |
| 混用不同 SDK 版本编译的原生插件变慢 | ABI 1.2 检测到类型化方法表或异步结果布局摘要不匹配，自动降级为按方法名 CBOR 分派 | 属于防崩溃保护行为；用同一版 `cordis-sdk` 重新编译两端插件即可恢复类型化直调 |
| `cordis pack` 报告私有路径 | 产物含本机 HOME 或用户名 | 推论 2，见[打包](packaging.md) |
