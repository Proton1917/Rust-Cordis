# 调用、超时与长任务

本篇展开[推论 3](principles.md)中截止时间、执行线程与事件循环三种资源。调用外部大模型、第三方 API、转码、批处理这类要等几十秒到几分钟的工作，是实际应用里最常见的需求，也最容易把插件写死。下面先给出 Rust-cordis 的事实，再给出由此推出的写法。

## 核心对调用的约束

| 约束 | 数值（`cordis.toml` `[runtime]`） | 后果 |
|---|---|---|
| 经核心转交的调用有截止时间 | `invoke_timeout_ms`，缺省 30000 | 超时，调用方得到错误码 6 |
| 同一连接连续超时 | 3 次（中间没有任何一次按时完成） | 核心判定该插件进程失效，终止并按退避重启它，它提供的服务全部撤回 |
| 每个连接每个方向的在途请求 | 64 | 超出的请求排队，对该进程背压 |
| apply、效应清理 | 各 30000 毫秒 | 超时视为装载或清理失败 |
| 状态导出 | 5000 毫秒 | 超时导致替换或检查点失败 |

“经核心转交”包括：不同分组的原生插件之间、原生插件与进程插件之间、进程插件之间、页面与后端之间。只有同组原生插件之间的调用是直接调用，不经过核心。插件不应依赖自己在哪个分组，所以按“一定经过核心”来设计。

由此得到：**一个服务方法不能等待外部工作完成后再返回，只要这项工作可能超过截止时间。** 如果这样写，慢一点的外部服务就会让方法超时；连续三次，提供方整个进程被终止，同进程里的其他服务一起下线。

不要用调大 `invoke_timeout_ms` 解决：这是全局参数，调大后核心发现真正卡死的插件也要等同样久（推论 1.4：全局超时是所有插件共用的部署事实，一个方法慢是该插件自己的事实）。

## 长任务的写法：提交、执行、查询

任务的状态是业务事实，由提供任务的业务插件掌握。接口按三个动作设计：

```wit
package app:jobs@1.0.0;

/// 长任务：提交后立即返回编号，执行在提供方的任务中进行。
interface jobs {
    /// state 取 queued、running、done、failed、interrupted。
    record job {
        id: string,
        state: string,
        output: option<list<u8>>,
        error: option<string>,
    }

    /// 登记任务并立即返回编号；同一 key 重复提交返回同一编号。
    submit: func(key: string, input: list<u8>) -> result<string, string>;
    /// 查询任务；编号不存在时返回 none。
    get: func(id: string) -> result<option<job>, string>;
    /// 请求取消；任务已结束时返回 false。
    cancel: func(id: string) -> result<bool, string>;
}
```

WIT 的 `async func` 只表示方法本身是异步实现，调用仍受截止时间约束，不能代替上面的拆分。

提供方：

1. `submit` 只做登记：把任务记录写进插件数据目录（或数据库），立即返回编号。用调用方给的幂等键去重，调用方超时后重试不会产生第二个任务。
2. 执行在实例拥有的任务里进行：Rust `ctx.spawn`（需要阻塞库时 `ctx.spawn_thread`），Python 与 TypeScript `context.task`。外部调用设置自己的超时，不依赖核心的截止时间。
3. 每次状态变化写回任务记录。结果大时写成文件，记录里存路径，读取时用字节流对象（`cordis.byte-stream@1.0`）返回。
4. 实例被替换或停止时，效应清理取消正在执行的任务，并把它们标记为 `interrupted`。新实例在 apply 中读取记录，把 `queued` 与 `interrupted` 的任务重新排入执行。任务记录在数据目录里，不依赖状态导出，导出器 5 秒的上限不受任务数量影响。
5. 需要限流时（例如外部 API 的并发上限），并发数作为组件配置，由提供方的执行队列控制。

使用方：

- 调用 `submit` 拿到编号，再用 `get` 轮询；或者监听提供方派发的完成事件（跨进程事件只是通知，收到后仍用 `get` 取结果）。
- 页面通过后端的 HTTP 接口或服务方法查询进度，不让浏览器保持一个长调用。

## 执行模型：代码跑在哪个线程上

判断“这里能不能阻塞”之前，先知道代码由谁执行。下面是 Rust-cordis 的事实，规则都从这里推出。

**原生插件（cordis-host）：**

1. 每个原生分组是一个 `cordis-host` 进程。进程里有一个专门轮询插件代码的执行器，**缺省只有 2 个线程**，同组所有插件共用。
2. 核心转来的每次服务调用、每个 `ctx.spawn` 任务、每次跨进程调用的等待，都是这个执行器上的任务。同步服务方法也在这里执行：它被包在一个任务里，在这 2 个线程之一上运行到返回。
3. SDK 自己提供的同步调用（同步接口方法的代理、`context.get` 等）以及 `Context::wait` 都经宿主的等待入口执行：等待期间，宿主把这个线程上的其他任务交给别的线程，执行器不会被占住。
4. 插件自己调用的 `futures::executor::block_on`、自建运行时的 `block_on`、`reqwest::blocking` 这类阻塞等待，宿主看不到，**会一直占住一个执行器线程**。

推论：在同步服务方法或 `ctx.spawn` 任务里用自己的 `block_on` 等待 SDK 的异步调用（例如 `secrets.get`、`http_api::page_attributes`、异步接口方法、字节流读取），等的那个调用本身也要在同一个执行器上运行。只要有 2 个这样的调用同时发生，2 个线程都被占住，等待的任务永远得不到运行：调用在截止时间到达时返回错误码 6，连续 3 次后整个分组被核心终止。并发越高越容易出现，单人测试通常发现不了。

**Python 与 TypeScript 进程插件：** 每个进程一个事件循环，所有请求、任务和回调共用它。任何同步阻塞都会停住整个进程。

## 阻塞的规则

- **Rust：**
  - 异步方法、apply 与 `ctx.spawn` 任务中，用 `.await` 等待。
  - 同步服务方法或 `ctx.spawn_thread` 线程中需要等待异步 SDK 调用时，用 `context.wait(future)`，例如 `context.wait(secrets.get(name))`。签名为 `Context::wait<F, T>(&self, future: F) -> Result<T>`，其中 `F: Future<Output = Result<T>>`；Future 可以借用局部值，不要求 `Send`，可以嵌套。它要求 SDK 0.2.1 及以上、宿主 cordis-host 0.1.1（ABI 1.1）及以上；在旧宿主上返回错误码 3，Future 不会被执行。
  - 也可以把方法在接口中声明为异步（WIT `async func`，trait 中写 `async fn`）。从同步改为异步属于不兼容修改，发布新的接口主版本（见[接口版本与升级](versioning.md)）。
  - 不调用 `futures::executor::block_on` 或任何自建运行时的 `block_on`。
  - 外部 HTTP 请求在 `ctx.spawn` 的异步任务中用异步客户端发出；客户端需要 Tokio 时，使用插件自己的 Tokio 运行时，并把它的创建与关闭登记为效应（[资源与状态](resources-state.md) PR-3）。
  - 必须使用阻塞库时，放进 `ctx.spawn_thread` 的独立线程，循环中用 `context.is_current()?` 判断是否退出。阻塞发生在插件自己的线程上，执行器不受影响。
- **Python：** 插件运行在一个 asyncio 事件循环里，所有请求共用它。服务方法和任务中不做同步阻塞 I/O（`requests`、`time.sleep`、同步数据库驱动），否则这一进程收不到也回不了任何请求，其他调用跟着超时，连续三次后整个进程被终止。用异步客户端，或 `await asyncio.to_thread(...)` 把阻塞调用移出事件循环。
- **TypeScript：** 同理，不用同步 I/O（`fs.readFileSync` 读大文件、`execSync`、`Atomics.wait`），CPU 密集的计算放进 worker 线程。

## 错误码的处理

调用方要把下列错误当作正常情况处理：

| 错误码 | 含义 | 处理 |
|---|---|---|
| 4 | 对象或上下文失效：提供方被替换、重启，或可选依赖缺席；写入时也表示导出期间冻结 | 当前上下文仍有效时重新取服务；幂等的操作可以重试 |
| 6 | 截止时间到达 | 只对幂等操作重试；非幂等操作改为上面的提交与查询写法 |
| 7 | 调用被取消 | 通常由调用方自己取消（丢弃 Future、实例停用）引起，不重试 |
| 8 | 连接或上下文额度耗尽 | 降低并发或分批，不立即重试 |

替换提供方时，依赖它的使用方会随依赖变化重新加载。正在进行的调用可能以错误码 4 或 7 结束，这正是任务记录必须持久化、提交必须幂等的原因。

## 检查清单

- 没有可能超过 `invoke_timeout_ms` 的服务方法。
- 长任务有持久的任务记录、幂等提交、可查询的状态，替换后能接着执行。
- 外部调用有自己的超时和并发上限。
- Python 与 TypeScript 插件中没有同步阻塞 I/O；Rust 插件中没有自己调用的 `block_on`，同步上下文的等待都经 `context.wait`，异步任务中没有阻塞客户端。
- 调用方对错误码 4、6、7、8 有明确处理。
