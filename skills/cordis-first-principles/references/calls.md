# 调用、超时与长任务

调用外部大模型、第三方 API、转码、批处理这类要等几十秒到几分钟的工作，是实际应用里最常见的需求，也是最容易把插件写死的地方。本篇先给出核心对调用的约束，再给出长任务的写法。

## 核心对调用的约束

| 约束 | 数值（`cordis.toml` `[runtime]`） | 后果 |
|---|---|---|
| 经核心转交的调用有截止时间 | `invoke_timeout_ms`，缺省 30000 | 超时，调用方得到错误码 6 |
| 同一连接连续超时 | 3 次（中间没有任何一次按时完成） | 核心判定该插件进程失效，终止并按退避重启它，它提供的服务全部撤回 |
| 每个连接每个方向的在途请求 | 64 | 超出的请求排队，对该进程背压 |
| apply、效应清理 | 各 30000 毫秒 | 超时视为装载或清理失败 |
| 状态导出 | 5000 毫秒 | 超时导致替换或检查点失败 |

“经核心转交”包括：不同分组的原生插件之间、原生插件与进程插件之间、进程插件之间、页面与后端之间。只有同组原生插件之间的调用是直接调用，不经过核心。插件不应依赖自己在哪个分组，所以按“一定经过核心”来设计。

由此得到：**一个服务方法不能等待外部工作完成后再返回，只要这项工作可能超过截止时间。** 如果这样写，慢一点的外部服务就会让方法超时；连续三次，提供方整个进程被终止，同进程里的其他服务一起下线。

不要用调大 `invoke_timeout_ms` 解决：这是全局参数，调大后核心发现真正卡死的插件也要等同样久（判据 5：不为单个使用方开特例）。

## 长任务的写法：提交、执行、查询

任务的状态是业务事实，由提供任务的业务插件掌握。接口按三个动作设计：

```wit
package app:jobs@1.0.0;

/// 长任务：提交后立即返回编号，执行在提供方的任务中进行。
interface jobs {
    /// state 取 queued、running、done、failed、interrupted。
    record job {
        id: string,
        state: string,
        output: option<list<u8>>,
        error: option<string>,
    }

    /// 登记任务并立即返回编号；同一 key 重复提交返回同一编号。
    submit: func(key: string, input: list<u8>) -> result<string, string>;
    /// 查询任务；编号不存在时返回 none。
    get: func(id: string) -> result<option<job>, string>;
    /// 请求取消；任务已结束时返回 false。
    cancel: func(id: string) -> result<bool, string>;
}
```

WIT 的 `async func` 只表示方法本身是异步实现，调用仍受截止时间约束，不能代替上面的拆分。

提供方：

1. `submit` 只做登记：把任务记录写进插件数据目录（或数据库），立即返回编号。用调用方给的幂等键去重，调用方超时后重试不会产生第二个任务。
2. 执行在实例拥有的任务里进行：Rust `ctx.spawn`（需要阻塞库时 `ctx.spawn_thread`），Python 与 TypeScript `context.task`。外部调用设置自己的超时，不依赖核心的截止时间。
3. 每次状态变化写回任务记录。结果大时写成文件，记录里存路径，读取时用字节流对象（`cordis.byte-stream@1.0`）返回。
4. 实例被替换或停止时，效应清理取消正在执行的任务，并把它们标记为 `interrupted`。新实例在 apply 中读取记录，把 `queued` 与 `interrupted` 的任务重新排入执行。任务记录在数据目录里，不依赖状态导出，导出器 5 秒的上限不受任务数量影响。
5. 需要限流时（例如外部 API 的并发上限），并发数作为组件配置，由提供方的执行队列控制。

使用方：

- 调用 `submit` 拿到编号，再用 `get` 轮询；或者监听提供方派发的完成事件（跨进程事件只是通知，收到后仍用 `get` 取结果）。
- 页面通过后端的 HTTP 接口或服务方法查询进度，不让浏览器保持一个长调用。

## 阻塞与事件循环

- **Rust：** 服务方法是同步函数，只做登记、查询这类短操作。外部 HTTP 请求放在 `ctx.spawn` 的异步任务里，使用异步客户端；在异步任务里调用阻塞客户端（例如 `reqwest::blocking`）会阻塞执行器线程，有的库还会直接 panic。必须用阻塞库时放进 `ctx.spawn_thread`，循环中用 `context.is_current()?` 判断是否退出。
- **Python：** 插件运行在一个 asyncio 事件循环里，所有请求共用它。服务方法和任务中不做同步阻塞 I/O（`requests`、`time.sleep`、同步数据库驱动），否则这一进程收不到也回不了任何请求，其他调用跟着超时，连续三次后整个进程被终止。用异步客户端，或 `await asyncio.to_thread(...)` 把阻塞调用移出事件循环。
- **TypeScript：** 同理，不用同步 I/O（`fs.readFileSync` 读大文件、`execSync`、`Atomics.wait`），CPU 密集的计算放进 worker 线程。

## 错误码的处理

调用方要把下列错误当作正常情况处理：

| 错误码 | 含义 | 处理 |
|---|---|---|
| 4 | 对象或上下文失效：提供方被替换、重启，或可选依赖缺席；写入时也表示导出期间冻结 | 当前上下文仍有效时重新取服务；幂等的操作可以重试 |
| 6 | 截止时间到达 | 只对幂等操作重试；非幂等操作改为上面的提交与查询写法 |
| 7 | 调用被取消 | 通常由调用方自己取消（丢弃 Future、实例停用）引起，不重试 |
| 8 | 连接或上下文额度耗尽 | 降低并发或分批，不立即重试 |

替换提供方时，依赖它的使用方会随依赖变化重新加载。正在进行的调用可能以错误码 4 或 7 结束，这正是任务记录必须持久化、提交必须幂等的原因。

## 检查清单

- 没有可能超过 `invoke_timeout_ms` 的服务方法。
- 长任务有持久的任务记录、幂等提交、可查询的状态，替换后能接着执行。
- 外部调用有自己的超时和并发上限。
- Python 与 TypeScript 插件中没有同步阻塞 I/O；Rust 异步任务中没有阻塞客户端。
- 调用方对错误码 4、6、7、8 有明确处理。
